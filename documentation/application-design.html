Application architecture

Application shell and routing

A shared application entry point that routes people into authoring or chain tracking without coupling either workspace to the other.

Status: routing direction agreed. The shared switch remains visible, Home remains the explicit root destination, declaration-level deep links are postponed, and Settings uses a route-backed overlay. The dedicated Chain Tracker design owns behavior inside its route boundary. Local runtime, packaging, persistence, filesystem, security, and test boundaries are settled in Application Architecture.

Purpose and Scope

The application has two major workspaces:

  • Editor: create, validate, and preview Jumpchain packages.
  • Chain Tracker: import jumps, make selections, and carry state from one jump to the next.

The shell owns entry, navigation, restoration, global settings, and route-level failures. Each workspace owns its internal tools and state. Detailed tracker behavior belongs to the separate Chain Tracker design.

Agreed Route Model

Use normal path-based URLs and browser history rather than hash routes. A direct URL should open the corresponding workspace, while Back and Forward should reverse user-visible route changes.

/Start screen and recent workNever silently redirects; offers explicit Resume actions.

Workspace and chain identifiers are application-generated opaque IDs. Local paths, document contents, selections, and permission tokens must not be embedded in URLs.

Route State Versus Workspace State

URLs identify meaningful destinations, not every transient control. The selected Editor declaration, panel sizes, folded groups, scroll positions, preview selections, and open diagnostics belong to workspace or session state. Stable declaration-level links are explicitly postponed beyond v1 and may be reconsidered only when there is a concrete sharing or restoration need.

Route-Backed Settings Overlay

Opening Settings from Home, Editor, or Chain Tracker pushes /settings while retaining the prior route as its background location. Settings appears as a modal layer beginning immediately below the router location bar, the underlying workspace remains mounted and inert, and Back or Close restores the prior route and focus. A refresh or direct visit to /settings has no background location, so the same Settings content renders as a normal full-page destination.

Home Organization

Home presents recent Editor workspaces and Chains in separate sections so their origin and available actions remain obvious. Each section shows at most five records and links to its owning hub when more records exist. The chain list places starred chains first, preserves last-opened ordering within the starred and unstarred groups, and displays a non-interactive accent star beside starred entries. Starring remains an explicit action on the Chain Tracker hub. Editor entries use the package/project name. Chain entries use the chain or profile name supplied by the user. Display names are labels rather than identifiers, so duplicate names remain valid and opaque route IDs distinguish their records.

Chain Tracker Hub

The /chain hub is the complete saved-chain registry rather than another recent-work summary. It places starred chains before unstarred chains and preserves last-opened ordering within both groups. Each card shows the chain’s name, Jump count, recency, editable description, and a large borderless star control whose active state uses the application accent, alongside explicit Open and Edit Details actions. Editing expands the selected card vertically while preserving its single-column width and neighboring card. The page heading, named-chain creation block, and saved-list heading and search remain fixed while the card list scrolls independently. Search matches both names and descriptions. Hovering or focusing a chain’s letter avatar reveals a smaller, non-interactive projection of its 12-axis perk-tag radar. The preview is positioned against the viewport, flips horizontally when necessary, and is vertically clamped so opening the final saved-chain preview never expands or jitters the independently scrolling list. A new chain requires a non-empty user-provided name, receives an opaque application ID, and opens immediately. Editing its name or description changes presentation data only; it never changes the route ID or chain contents. The chosen application accent colors secondary action outlines, discovery links, interactive hover fills, and the new-chain callout while structural boundaries remain neutral. The default-off chain.colorNamesByPrimaryTag setting may color a saved chain’s name from the top-level tag category containing its greatest eligible radar count. That count includes Jumper and form perks by default, can include their items through chain.includeItemTagsInRadar, and always excludes companion-owned records.

Navigation and Restoration Rules

  1. Only explicit user activation changes the top-level route.
  2. The persistent Editor and Chain Tracker controls always target their hubs; specific recent records open only through explicit Resume actions.
  3. Every route change adds or restores a browser history entry; it does not simulate navigation only inside component state.
  4. The shell updates the document title and moves focus to the destination heading after a route transition.
  5. Editor autosave flushes before leaving its route. In explicit-save mode, unresolved changes require a leave confirmation.
  6. Returning to a mounted workspace restores its internal UI state when safe; reopening after a browser restart restores durable state and revalidates external permissions.
  7. An unknown or inaccessible workspace ID opens a recovery screen in the correct workspace hub instead of falling back silently to Home.
  8. Contextual Settings navigation retains the current workspace as an inert background; direct Settings navigation renders the same content as a full page.

The shell should not know Editor panes or Chain Tracker selection rules. Shared services expose capabilities through stable interfaces so the larger tracker can be loaded independently and developed later without making Editor startup pay its full cost. The centralized local diagnostic boundary is specified separately in Logging Design.

Chain Tracker Boundary

The current application design commits only to:

  • a distinct /chain hub and /chain/:chainId workspace route
  • independent durable chain records
  • the ability to consume validated Jump packages through the shared package model
  • a shell-level way to move between Editor and Chain Tracker

Tracker navigation, chronology, package selection, historical inventory, companions, supplements, and the shared-renderer boundary are maintained in the dedicated tracker document. This shell document continues to own only routes and shared application services.

Security and Privacy

  • URLs contain opaque local identifiers, never filesystem paths, document text, permission tokens, or choice data.
  • A restored route is not proof of access. Storage and file permissions are checked again before opening protected content.
  • History state remains small and non-sensitive; durable workspace data stays in the persistence layer.
  • Imported packages are untrusted input and pass through the same parsing, validation, asset, and rendering boundaries in both workspaces.

Accessibility Requirements

  • Route changes occur on activation, never merely because a navigation item receives focus.
  • Each route has a unique visible heading and descriptive document title.
  • After client-side navigation, focus moves predictably to the new route heading unless restoration returns the user to a known prior focus target.
  • The Settings overlay traps focus, closes with Escape, marks the background inert, and restores focus to its opener.
  • Persistent shell regions use semantic header, navigation, and main landmarks.
  • Back and Forward restore both the route and an understandable point in that route.

Decision Record: Route-Level Workspaces

Status
Accepted for the application-shell draft
Decision
Editor and Chain Tracker are independently addressable route-level workspaces under one shared application shell.
Why
They have different workflows, restoration needs, and implementation size, but share package parsing, settings, storage concerns, and product identity.
Consequences
The eventual local runtime must restore deep links or equivalent destinations; route transitions must integrate navigation history and accessibility; workspace state needs an explicit persistence boundary.

Research Basis

  • The browser History API supports path changes with associated serializable state and Back/Forward restoration through popstate. MDN History API guide
  • Hash routing is now a legacy fallback; normal path routing produces cleaner, independently addressable destinations. MDN hash routing overview
  • Single-page views need descriptive titles that change with their topic. W3C Page Titled guidance
  • Navigation must not occur merely because a control receives focus. W3C On Focus guidance

Settled Shell Decisions

  • The Editor/Chain Tracker switch remains visible inside active workspaces.
  • / always shows Home and offers explicit Resume actions rather than silently redirecting.
  • Declaration-level Editor URLs are postponed beyond v1.
  • Settings is a route-backed overlay when opened from another route and a full page when opened directly.
  • Home separates recent Editor workspaces from Chains, limits each group to five records, and links to the owning hub when more exist; starred chains appear before unstarred chains, retain recency ordering within each group, and use a read-only accent star on Home.
  • Switching workspaces through the persistent Editor/Chain Tracker controls opens the destination hub; it never chooses a recent project or chain automatically.
  • No other action receives permanent shell space in v1. Create, import, export, search, documentation, and other contextual actions remain in their owning hub, workspace, or Settings page.

Application Shell Status

Implementation status: the primary shell, five-item Home recent lists, durable chain starring and grouped-recency ordering, Editor hub and workspace boundary, complete searchable and independently scrolling Chain Tracker saved-chain hub, named-chain creation, editable chain names and descriptions, read-only radar summaries, active Chain Tracker composition, browser history, route titles, route focus, workspace-specific recovery, and the route-backed Settings surface are implemented. Settings preferences, tag profiles, and diagnostics use their real browser and desktop durability boundaries; session logs, notifications, and crash state deliberately remain launch-local. The Editor will adopt the same five-item Home limit when its project hub is implemented. Review fixtures remain direct development routes and are not part of product navigation.

No application-shell interaction questions remain open for v1. The local-runtime boundary is maintained separately in Application Architecture.
