Chain workspace draft

Chain Tracker design

An ordered, persistent chain workspace for choosing jumps, making selections through the shared Jump renderer, and inspecting everything accrued at any point in the chain.

Status: workspace direction settled for the current scope. The major surfaces, reordering review behavior, chain-wide supplements, immutable package versions, markup-derived companion viewpoints, and always-editable Jump entries are established. Supported supplement modules are discussed in Supplements Design.

Purpose and Boundary

The Chain Tracker owns a user’s durable chain record. It consumes validated Jump packages but never edits their source. The initial workspace must support:

  • an ordered list of jumps already in the chain
  • a library of built-in and imported jumps available to add
  • drag, keyboard, and button-based jump reordering
  • the current jump’s interactive choices, costs, and rolls
  • perks, items, and companions accrued through any selected chain point
  • tag filtering over accrued perks and items
  • alternate forms accrued through the chain, with the same historical inspection pattern as companions
  • supplements that can be enabled, disabled, opened, and configured, including persistent foundations such as Body Mod

Core State Model

A chain contains ordered chain entries, not merely package references. Each entry has its own stable ID, immutable installed-package version, choice state, rolls, grants, and validation status. Supplement state is owned once by the chain. The same logical package may appear at different installed versions without attaching accrued content to a fragile array index. The user setting gates only an interactive attempt to add a second version; it does not govern imported or already-present entries.

Current jump

The entry open for choice interaction. Selecting a chain entry also makes it the default historical cutoff.

Inspection point

The inclusive “through this jump” boundary used by Perks, Items, and Companions. It may be changed without opening another jump.

Jump library

Validated built-in and imported packages available to add. Library membership is independent from chain membership.

Supplements

Chain-wide, application-defined rule/content layers with explicit enabled state and their own selections. The supported set and module-specific behavior are documented separately.

Duplicate Jump Entries

The chain.allowDuplicateJumps setting permits the user to add the same exact installed Jump package to one chain more than once. Every addition creates a distinct chain entry with its own stable ID, chronology, choices, rolls, grants, actor state, and supplement state. It does not reopen, clone, or mutate an existing entry.

When the exact package is already present and duplicate Jumps are disabled, its Library action reads Open chain entity. When duplicates are enabled, the action reads Add to chain again (xN), where N is the number of instances that will be present after pressing it—for example, adding a second instance reads Add to chain again (x2). The first instance continues to use Add to chain.

Repeated acquisitions project into Inventory through quantity aggregation. With the default-on chain.aggregateSimilarInventory setting, records with the same owner, perk/item kind, resolved name, and rank combine into one result whose xN badge is their summed copy count, even when their packages and grant handles differ. Perks and items never combine, and different ranks remain separate results. Repeated ranked acquisitions at the same rank show both the ordinary rank badge and xN; a quantity-measured grant shows xN without a rank badge. The aggregate uses the union of its constituent tags. The shared detail surface retains every contributing source and conditionally resolved description, with four or more acquisitions constrained to an independently scrolling list.

Earth and Evaluated Identity

Every chain begins with one system-owned, unnumbered Earth entry before Jump 1. Earth is not an installed package, is absent from the Library, and cannot be moved or removed. It supplies Origin Human, Location Earth, and 0 CP while exposing free, initially unset Gender and Age controls. It appears as the oldest historical cutoff, where accrued content is empty.

The chain rail uses the shared application context menu. Ordinary rows expose Open, Move earlier, Move later, and Remove while retaining dependency review. Earth exposes only Open identity setup and conditional Clear starting Gender or Age actions. Opening selects Earth without mutating either value; clearing uses the same nullable choice commands as its visible controls. Earth never receives reorder or removal actions.

The tracker consumes evaluated entry properties rather than inferring identity from display labels or choice handles. Origin and Location are current-entry values and never inherit. Gender and Age use their authored previous/original continuity rules. Species uses an explicit current-entry property first, then an enabled Classic Body Mod Bestial label, then Human. Missing Origin, Location, Gender, or Age renders as Unknown; that word is never stored as a value.

Native and Applied Gauntlets

A native Gauntlet is declared by its immutable installed package. An ordinary Jump may instead receive entry-scoped Gauntlet rules through a deliberate user action or an active supplement such as an applicable Universal Drawbacks rule. The tracker stores every active source with provenance and evaluates one idempotent Gauntlet condition; it never changes installed markup, permits a native Gauntlet to be turned off, or stacks the starting-point reduction.

Gauntlets remain ordinary chronological entries for numbering, historical cutoffs, Inventory, Story, and provenance. The rail keeps the number and adds a visible Gauntlet badge; the workspace kicker reads, for example, Gauntlet 3 of 8. Library cards identify native Gauntlet packages, while an applied badge belongs only to the affected chain entry and identifies its source on inspection.

Jump imagery is promoted atomically. A selected Jump first renders as an inert, invisible staging workspace and every rendered image must finish decode() before that same DOM workspace becomes visible. This gate applies to Jump-to-Jump selection, returning from Inventory or another Chain Tracker tab, and the initial Chain Tracker route mount. With no previously promoted Jump, a stable preparation surface occupies the workspace; an incomplete Jump is never revealed as a timeout fallback. Pointer and keyboard intent may still preload package assets, but rendered-image decoding remains the final authority.

For the Jumper, a native Gauntlet contributes its authored starting points or the native default of 0. Applying Gauntlet rules to an ordinary entry changes its ordinary starting-point contribution to 0. Drawbacks, Quest awards, and other explicit grants still add to the same resource ledger; purchases continue to subtract. Companion participation and allowances remain controlled by explicit import grants rather than being inferred from the Jumper’s Gauntlet base.

Reordering and Historical Views

Accrued records refer to the stable ID of the chain entry that granted them. Chronological numbering still begins with Jump 1, but the list renders newest-first: the most recent entry is at the top and Jump 1 is at the bottom. Reordering changes chronology and therefore changes what appears at each historical cutoff, but it does not detach a perk, item, or companion from its originating entry. Reordering remains freely available. The default-off chain.warnUpstreamChanges preference may request review before a reorder or deletion invalidates an explicit active downstream reference, such as moving a companion provider after a Jump that imports that companion. Ordinary record-volume and historical-cutoff changes never trigger the warning. Every committed reorder or deletion offers Undo in the shared Chain activity notification stack. The notification follows the global enablement, class, maximum-visible, duration, pause, and dismissal settings.

No Completion State

A Jump entry is never completed, finalized, locked, or reopened. Users may make any number of choices—including none—and may return to edit any entry at any time. The tracker continuously recalculates costs, grants, historical views, and downstream diagnostics from the current state.

Shared Jump Renderer

The Editor preview and the Chain Tracker must use the same package renderer, layout engine, condition evaluation, choice controls, roll controls, and responsive behavior. The renderer receives a state adapter:

  • Editor preview adapter: temporary, non-persistent choices used to inspect authoring changes.
  • Chain adapter: durable choices, rolls, costs, grants, and diagnostics associated with one chain-entry ID.

This keeps a Jump from looking or behaving differently when authored and when actually used. The tracker surrounds the shared renderer with chain chronology, inventory, companions, and supplement tools; it does not fork the renderer.

Interactive Workspace Draft

Use the five primary workspace tabs, newest-first chain, reorder controls, library, historical selectors, tag filters, choices, rolls, and supplement subtabs. The mock keeps a fixed workspace frame. Chain & Jump has independent rail and rendered-Jump scrollers; its containing page does not add a third vertical scroller. Other workspace pages own one intentional content scroller. This fixture assumes the parallel-package-version and negative-point-balance settings are enabled so both states can be exercised.

Workspace Rules Captured by the Mock

  1. Chain & Jump, Inventory, Forms, Companions, and Supplements are independent full workspace pages rather than persistent side panels surrounding one main page.
  2. Selecting a chain entry keeps the Chain & Jump page open and sets the inspection point to that entry.
  3. Changing only the inspection point updates Inventory, Forms, and Companions without changing the open Jump.
  4. Inventory contains only the Jumper’s accrued perks and items, can filter to either kind, and reuses relationship-aware search behavior from Tag System Design. Companion-owned perks and items remain on that companion’s profile instead of appearing in the Jumper’s Inventory search, count, or Stats. Each result card shows every tag when it has five or fewer. Longer tag lists show five badges and an ellipsis whose hover and focus tooltip contains the complete list; tags responsible for the active text search or relationship filter receive priority within the five visible positions while retaining authored order. The Stats subtab counts Jumper and form perk tags by default. The optional item-tag setting also counts Jumper and form items; companion perks and items never affect the radar.
  5. Selecting an Inventory result opens its complete record—including every constituent source and description, the union of its tags, modeled rank or quantity metadata, and aggregate count—in a reusable perk/item detail overlay. Numeric visible grants default to rank unless measure: quantity explicitly identifies interchangeable copies. Four or more constituent acquisition rows scroll independently inside the fixed-width dialog.
  6. Forms use the same historical roster-and-detail interaction as Companions. They are accrued records to inspect, not mutually exclusive states to activate. Each form’s full-details overlay shows form-specific properties and perks, and those perks open the shared record-detail overlay.
  7. Reordering preserves each entry’s identity and grants, then recomputes historical views and dependency diagnostics. Dragging shows an accent-colored insertion line between entries at the exact drop position. With upstream warnings enabled, only a reorder that would invalidate an explicit active downstream reference requires review before it commits; the preference is off by default.
  8. The × control removes a chain entry while preserving the source package in the library. The removed entry’s choices, rolls, grants, and actor state are deleted rather than retained for a later re-add. Up, down, drag, and remove controls use the same compact action pattern as layout editing.
  9. The library identifies built-in, imported, and application-owned Mock provenance and always distinguishes separately installed versions. Mock packages are absent, including their source filter, unless Developer → See Mock Data is enabled. Adding an exact version already in the chain focuses its entry. When the user invokes Add for another version of the same logical package, that one action is permitted only by the user setting. Importing a chain, installing packages, disabling the setting later, and using entries already in the chain do not consult it. Multiple present versions are always surfaced on chain entries and historical selectors.
  10. The duplicate-Jump setting is independent from multiple-version support. It changes an already-present exact package’s Library action from Open chain entity to Add to chain again (xN) and creates another independent entry. Disabling it later leaves existing duplicates intact.
  11. A native Gauntlet is visibly identified in both Library and chronology. An ordinary entry exposes an Apply Gauntlet rules action directly below the fixed-width actor selector rather than beside the variable-length Jump title. Applying or removing that entry modifier is autosaved and undoable; a native Gauntlet has no remove-Gauntlet action.
  12. The current-jump summary exposes currency, origin, gender, and age without consuming renderer space. Switching the active actor loads separate choice state. A companion appears in the actor selector only after that companion is purchased in the current Jump or selected by an active companion-import grant, and a positive resource grant explicitly targets that companion handle. Companion-targeted perks accrue to the companion profile but do not imply participation without usable currency.
  13. Currency details expose the Gauntlet base, Chain and Single-Jump drawback awards, Quest or supplement awards, purchases, and final balance as separate provenance-bearing terms. A zero Gauntlet base never hides later grants.
  14. The compact summary keeps the primary currency and origin names visible. Hovering or focusing Currency shows the active actor’s remaining alternative currencies. Hovering or focusing Origin shows property provenance and description plus the independently evaluated Species and Location. Unset Origin or Location is displayed as “Unknown.” One Origin choice may deliberately grant both properties, but the tracker never implies Location from Origin.
  15. The Supp button beside + Add opens an overlay without resizing the workspace. In the application shell it uses the same application-level modal layer, centering bounds, maximum surface size, backdrop, and responsive behavior as contextual Settings rather than positioning itself within the Jump pane. The backdrop begins exactly below the router location bar, covers the workspace tabs and content, and leaves the application navigation available. It lists only enabled supplement tools for the selected Jump, and updates its title and content when another Jump is selected.
  16. Negative point balances are disabled by default. When disabled, the renderer rejects only a user action that activates a choice, increases a selected rank, or selects a rolled result when that active selection would create or worsen a negative primary Jump-point balance. The resulting “Choice rejected, negative balance” toast uses an X icon and red edge. Clearing or deselecting a choice, reducing a rank, and non-choice recalculation always proceed even if the resulting balance is negative. When enabled, those active selections may overspend.
  17. Rail metadata exposes its complete text on hover only when the visible line is actually truncated. The “Current Jump” kicker is fixed black on the pale Jump surface and does not inherit the application accent.
  18. Renderer implementation labels are not user-facing. The optional Developer setting may show only Format 1 evaluated package above an ordinary Jump; it is off by default and Earth never shows a diagnostic label.
  19. An allowed deficit turns the current balance red, marks the affected companion option in the actor selector, and marks the Jump in both its header and chain entry. These indicators clear automatically when every actor returns to a nonnegative balance.
  20. The companion detail can open a route-style overlay showing that companion’s perks, items, and Jump import history. Perk and item columns show up to five action rows before scrolling; the denser import-history column shows up to nine entries before using the same bounded height. Empty columns replace their heading and blank list with “Companion has no perks,” “Companion has no items,” or “Companion has not been imported into any jumps.” Profile record hover and focus treatments derive their border, tint, and outline from the configured application accent. Selecting one of its perks or items opens the same record-detail overlay above the companion profile rather than replacing it.
  21. Supplements are chain-wide and application-defined rather than author-defined markup packages. The Supplements page always retains a Manage subtab. Each enabled supported supplement gains its own content subtab; disabling it hides that reserved subtab without deleting its selections or shifting adjacent controls. Module-specific main pages and current-Jump tools belong to Supplements Design.
  22. Jump entries have no completion state or minimum-choice requirement. They remain editable for the life of the chain.
  23. All choice and roll interaction inside Jump or supplement content uses the shared renderer contract.

Persistence and Recovery

  • Choice changes, rolls, reordering, and supplement toggles autosave with the same explicit-save fallback available elsewhere in the application.
  • Enabling or disabling a supplement recalculates every Jump and historical view. Disabled modules retain their choices and records but contribute no active rules, grants, costs, restrictions, or resource transformations.
  • Manually applied Gauntlet state is chain-owned and persists independently of any supplement source. Supplement-owned sources disappear from active evaluation when their module is disabled but retain their module state; removing the last applied source restores an ordinary package’s starting-point contribution.
  • A supplement toggle never fails or deletes purchases merely because recalculation creates a deficit. The resulting recovery deficit is allowed regardless of the ordinary negative-balance setting. Only a later active choice selection that would create or worsen a negative primary Jump-point balance consults that setting.
  • Each chain entry is permanently associated with the installed package version used to create it. Installing another version does not alter or migrate that entry.
  • The application-owned Morgan Mock chain is the sole exception to ordinary exact-version pinning: when a development build replaces one of its three canonical Mock packages under the same stable package identity, the saved entry is rebound to that current fixture while its choices, inputs, and rolls are preserved. Morgan is hidden from saved-chain lists when See Mock Data is off, although an already-open or direct route remains usable. Reset Mock Data recreates a deleted Morgan or replaces it with a fresh canonical filled-in state. User-created chains and non-canonical packages retain strict exact-version recovery behavior.
  • In-chain package updating and migration are not supported. To use a different version, the user removes the old entry and adds the separately installed new version, accepting the normal removal impact review and rebuilding its selections.
  • Removing a package from the library does not destroy chain entries already based on it; the stored snapshot remains usable.
  • An installed version that becomes unavailable leaves its chain entry recoverable from retained chain data; the application does not silently substitute another installed version.
  • Reordering and deletion are undoable. When chain.warnUpstreamChanges is enabled, a change that would invalidate an explicit active downstream reference receives pre-commit review. Unrelated changes commit without confirmation, and disabling the preference skips review without weakening validation or Undo.
  • Removing a jump is also undoable and reports any grants, companion imports, forms, or downstream dependencies that will leave the active chronology.
  • Negative balances are ordinary persisted actor state. Turning the setting off does not silently undo choices and does not turn the setting into a general validity gate. It blocks only later active choice selections that would create or worsen a negative primary Jump-point balance; clearing, deselection, rank reduction, and non-choice recalculation remain available.

Accessibility and Safety

  • Every drag operation has equivalent up/down controls and keyboard ordering support.
  • Tabs, chain entries, tag filters, choice controls, and supplement toggles expose selected state programmatically.
  • The contextual supplement overlay is keyboard reachable, identifies the selected Jump, exposes each selected tool programmatically, and closes with Escape while returning focus to Supp.
  • Historical filtering announces updated counts without moving focus or resetting the current workspace tab.
  • Imported packages, Markdown, images, and assets remain untrusted and use the same sanitization and permission boundary as Editor preview.
  • Roll outcomes are announced and stored; animation is never the only indication that a roll completed.
  • Disabling a supplement never silently deletes its selections. The state remains available if it is re-enabled.
  • The supplement, companion profile, form profile, and perk/item detail overlays share Settings’ application-level backdrop boundary, focus containment, Escape-to-close, inert-background, and focus-restoration rules. Navigating away from the active Chain Tracker route closes each of these overlays immediately; none remains mounted to reappear when the chain is reopened.
  • When overlays are stacked, only the top overlay receives interaction. Closing a perk/item detail restores focus to its invoking Inventory card, companion record, or form-perk record, leaving the underlying profile open.
  • Negative balance state is communicated by signed point text, warning language, and an icon in addition to red styling.

Light-theme Tracker Presentation

In explicit Light mode, the primary tabs, Chain/Library rail, Library package cards, jump entries, route controls, Inventory Search and Stats, Forms, Companions, Supplements Manage, module pages, inputs, buttons, scroll areas, profile/detail dialogs, inline dialogs, and hover/focus states use the shared warm-neutral light palette. The intentional document styling inside the Jump renderer remains authored content rather than tracker chrome. Muted text must remain readable at 4.5:1 and meaningful control or focus boundaries at 3:1.

Tracker light rules never alter the established dark presentation. The sole both-theme exception is scoped to .tracker-supp-context: “Current-Jump Supplements” and “Selected Jump · …” use the accessible active-accent text token, while the selected supplement’s left rail uses the raw active accent. Main Supplements pages and every non-contextual supplement dialog retain their module palettes.

Current Design Status

Implementation available. The real /chain/:chainId route and deterministic review harness use the reusable tracker workspace, Format 1 parser, pure chain evaluator, and shared Jump renderer. Choice state, rolls, balances, identity, Inventory, tags, radar values, Companions, Forms, dependency warnings, Gauntlet state, and supplement projections are evaluated from exact package references. The mock above remains the visual and behavioral authority.

The duplicate-Jump setting, explicit Format 1 measures, and form grants are implemented. Other Chain Tracker workspace decisions are settled for the current scope. The supported supplement set and its current module-specific decisions remain in the dedicated supplement document.
