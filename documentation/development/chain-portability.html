Portable chain contract

Chain export and import

A portable chain preserves the user’s chain state and separately owned supplement data while referring to installed Jump packages by exact content identity. It does not redistribute those packages.

Status: agreed portability contract; local aggregate persistence implemented. Physical format, package references, missing-package behavior, supplement inclusion, forward compatibility, atomic validation, copy-based import, and export scope are settled. Saved chains already persist as independent versioned aggregates through IndexedDB or SQLite; the user-facing .jchain archive transfer remains a separate implementation increment.

.jchain Portable Container

A portable chain uses the user-facing .jchain extension and is internally a ZIP archive. The extension keeps the implementation detail out of ordinary file handling while allowing chain, supplement, and Story state to remain independently versioned.

The format 1 archive contains only these root structures:

  • manifest.json — required container format, exporting application version, state-schema requirements, and a file table containing each payload’s path, uncompressed byte length, and SHA-256 digest
  • chain.json — required authoritative chain metadata, chronological entries, actor state, selections, rolls, balances, accrued records, unresolved-package snapshots, and package references
  • supplements/<module-key>.json — one versioned state document for every supported supplement with preserved state, whether enabled or disabled
  • story.json — the separately versioned editable Story supplement state

No Jump package, asset, executable, arbitrary attachment, settings profile, or extra archive path is permitted. JSON is UTF-8, rejects duplicate object keys, and uses arrays wherever source or chronological order is meaningful.

Export Boundary

A chain export contains the complete portable state needed to reconstruct the chain but does not embed any .jmp package or its assets. Exported state includes:

  • chain name/profile metadata, the system-owned Earth identity entry, and chronological installed-Jump entry records; Earth’s user-facing status is always reconstructed as The Beginning rather than trusted from stored presentation data
  • package references, selections, rolls, actor state, balances, accrued records, forms, companion participation, entry-applied Gauntlet sources, and provenance
  • all enabled and disabled supplement state, stored per module rather than folded into Jump data
  • Story chapters and their editable source representation
  • schema and module-state versions needed to validate or migrate the export

Application settings, the user’s tag profile, session logs, filesystem paths, permission handles, and installed package bytes are not chain state and are not included.

Earth is serialized as a distinguished application-owned entry, never as an installed-package reference. Its selected Gender and Age values are portable actor state; Origin Human, Location Earth, 0 CP, immutability, and unnumbered chronology are system semantics reconstructed by the importing application. Unknown presentation text is not serialized.

Native Gauntlet status remains immutable package metadata recovered from the exact installed package reference. A manual Apply Gauntlet rules action is chain-entry state and exports with its stable source identity. Supplement-applied Gauntlet sources remain in their owning module documents. Import recomputes one effective status from those sources; it never serializes only the derived boolean or bakes a supplement effect into package metadata.

Exact Package References

Every chain entry references an installed Jump using both readable metadata and the cryptographic hash of the complete installed .jmp byte stream.

  • Readable metadata contains the normalized logical identity—Jump name plus the order-independent author set—along with the displayed version.
  • The authoritative reference is SHA-256 over every byte of the installed .jmp file. The exported reference uses the form sha256:<64 lowercase hexadecimal digits>.
  • Name, authors, and authored version never substitute for a hash match. They exist for diagnostics, library search, and guided recovery.
  • Other installed versions with the same logical identity do not interfere when the exact referenced hash is installed.
  • A same-identity package with a different hash is surfaced as a version/content mismatch and is never silently attached to the entry.

Unavailable or Unreadable Jumps

Importing a chain never deletes an entry merely because its package cannot be found, opened, or parsed.

  • The entry remains selectable in chronology and is visibly marked with a package error.
  • Previously stored selections, rolls, accrued records, and actor state remain preserved and visible. They are not ignored or silently recalculated against another package.
  • The unresolved-entry snapshot preserves whether the missing exact package was natively a Gauntlet, so its last validated point and supplement projections remain explainable without allowing that snapshot to masquerade as a different installed package.
  • The Jump pane cannot render substantive package content or accept package-defined choices while the exact package is unavailable.
  • Chain-wide supplements remain usable for that entry. Story and other supplement state are independent of package readability.
  • Installing a readable package with the exact hash resolves the reference and triggers deterministic revalidation.

Multiple Versions and Guided Repair

The installed library may contain several hashes for one name-and-author identity. Exact hashes keep those versions distinct. A reference that can find only a different hash produces an import diagnostic with an optional How to fix this action. Instructions explain how to locate and install the referenced release, inspect installed versions, or manually remove and replace the chain entry. The application does not update an existing entry in place.

Setting boundary: importing an individual package uses normalized author set plus Jump name as its identity. The same identity and version is always rejected; a different version requires chain.allowMultiplePackageVersions. Archive-byte or package-local-ID differences never bypass those rules. A full chain import still preserves every exact package reference already declared by that chain, and turning the setting off later does not invalidate, remove, merge, or warn about versions already present.

Supplement and Story State

Supplement modules own their data independently from Jump entries even when a module records per-entry progression. The chain export includes each module’s versioned state alongside, not inside, package-defined choice state. Disabled modules export their preserved selections as well.

Story chapters therefore survive a missing Jump package and remain editable from the supplement surfaces. Chain portability preserves the editable Story representation. The separate human-readable Story export is plain Markdown as specified in Supplements design.

Atomic Import and Safety

Every chain export is untrusted input. The importer validates and stages the complete archive before creating any local record:

  • treat every chain export as untrusted input and validate its container, paths, sizes, compression ratios, schemas, counts, strings, hashes, and module-state versions before creating local records
  • reject path traversal, executable payloads, unexpected files, duplicate archive paths, oversized expansion, invalid Unicode, and unknown required structures
  • never trust exported local IDs as authority over existing records; allocate new local chain, actor, and runtime record IDs while preserving internal relationships through import-local mapping
  • show all blocking conflicts before committing and make import atomic, so a failed import creates no partial chain

Schema Compatibility

If the archive requires a newer chain schema, an unknown supplement module with preserved state, or a newer unsupported state schema for any included supplement, import rejects the entire archive with a compatibility message instructing the user to update the application. It never drops, guesses at, or preserves opaque state it cannot validate.

Supported older state schemas may be migrated deterministically in memory before the atomic commit. Import does not rewrite the selected .jchain file. A later export from the newly created local chain uses the application’s current supported schemas.

Copy-Based Import

Import always creates a new local chain with new internal chain, actor, and runtime-record IDs. Exported identifiers preserve relationships only within that import and never select or overwrite existing local records. The imported chain keeps its exported display name even when another local chain has the same name; names are presentation and need not be unique.

The portable export can be used as a manual backup, but importing it creates a copy rather than restoring over the original. Destructive in-place restore, automatic backups, and merge are intentionally outside the v1 portability contract.

Current-State Export

Portable export contains current authoritative chain and supplement state only. Undo stacks, activity history, route/session state, and diagnostic logs are local operational records and are not exported. This boundary does not exclude selected choices, recorded rolls, dormant input values, disabled supplement selections, Story chapters, unresolved-package snapshots, or provenance records; those are current authoritative state.

Security Consequences

  • Package hashes establish exact byte identity, not authorship, trustworthiness, safety, or endorsement.
  • Persisted accrued records from an unresolved package are user state, not executable instructions. They render only through application-owned record schemas.
  • Imported Story source uses the same strict sanitizer as locally authored Story content.
  • No imported path or identifier is allowed to select or overwrite an arbitrary local file or record.
