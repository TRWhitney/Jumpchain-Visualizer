PDF-to-.jmp Conversion Guide

A decision-oriented workflow for reproducing the content, mechanics, artwork, color, and composition of an existing Jump without hiding what Format 1 cannot express.

Status: reference workflow established. The supplied source is authoritative, semantic and visual fidelity are separate hard gates, and every approximation must be explicit and traceable. Apply the companion visual-fidelity protocol to every conversion.

Conversion contract

A complete conversion delivers an editable project, a validated .jmp, extracted graphical assets, and a ledger connecting every source block to its representation. It is not complete merely because the archive imports.

  • Content fidelity: every heading, instruction, option, cost, award, description, and outcome is transcribed or deliberately marked uncertain.
  • Semantic fidelity: selections, costs, grants, properties, rolls, quantities, and ownership behave like the source wherever the format supports them.
  • Interaction fidelity: controls, roll affordances, cost badges, and clearing behavior remain understandable and reachable.
  • Visual fidelity: measured source silhouettes, major bounds, artwork, palette, hierarchy, density, and column rhythm pass an equal-width comparison or are explicitly marked blocked.
  • Traceability: unsupported behavior is named in prose and the ledger instead of being approximated invisibly.

Working-area structure

Conversion inputs and copyrighted source assets belong in an ignored scratch tree. Only reusable process documentation and gap decisions belong in the repository.

scratch/conversion-name/
  source/                 # authoritative PDF and supplied references
  extracted/pages/        # lossless page renders used for comparison
  extracted/assets/       # reusable crops with source coordinates
  project/
    jump.jdef
    choices.jdef
    layout.jdef
    assets/
  conversion-ledger.json
  converted-jump.jmp
  extract_pdf.py
  build.mjs

Never place the source PDF inside a .jmp. The archive accepts definition files and validated graphical assets only, and its limits and path rules remain a security boundary rather than a conversion inconvenience.

Phase 1: establish source truth

  1. Record the exact supplied filename, page count, page dimensions, visible title, author, edition, and whether a selectable text layer exists.
  2. Hash or retain the original bytes unchanged. A web copy may clarify text but must not silently replace the supplied edition.
  3. Render every page losslessly. For an image-only PDF, inspect the embedded image streams before introducing resampling.
  4. Transcribe once from enlarged renders and a second time while comparing each block directly with its page.
  5. Mark each ledger entry verified, uncertain, or externally-corroborated. Never use “verified” for a guess.

Secondary sources are evidence only. Record the source and the exact uncertainty they resolved; retain the PDF wording when sources disagree.

Phase 2: build the semantic inventory

Inventory source concepts before writing declarations. Separate rules prose from actionable controls, and separate a thing's acquisition from its presentation.

Traits are the user-visible catchall for Jump-local circumstances. They render in the current Jump evaluation but are intentionally excluded from accumulated perk and item records. Do not convert a temporary biography, legal status, local curse, or insertion condition into a durable perk merely to make it visible.

Create a second, visual source-node inventory beside the semantic inventory. Every visible heading, side note, sentence, list line, price, rule, artwork unit, and deliberate empty region receives one source coordinate and one intended authored node. This catches omissions that a concept-only ledger misses. Source-facing Jump content must contain the source wording, not converter commentary or implementation disclaimers; put those in the ledger and persistent audit.

Phase 3: choose stable authoring identities

  • Generate lower-snake-case handles from semantic names, then resolve collisions deliberately. A renamed display label must not force a handle change.
  • Use one package-wide group label for true shared membership. Do not use groups as layout columns.
  • Use direct placement handles when individually selectable cards need an authored grid.
  • Give companions and forms explicit stable handles before authoring targeted perks, resources, or ownership.
  • Keep source order unless the source itself states another ordering rule.

Phase 4: assign tags

Tags describe searchable effects. They do not encode mechanics.

  • Prefer one to three concrete built-in tags such as survival, repair, telekinesis, communications, or wealth.
  • Add a narrow setting tag such as pokemon only when it materially improves search.
  • Put shared tags on the Choice so ordinary grants inherit them. Put tags on a block grant when one Choice creates records with different meanings.
  • Do not tag a cost, discount, prerequisite, rarity, source page, section name, or unsupported rule.
  • Avoid redundant perk, item, and companion tags when record kind already communicates the distinction.

Tag appearance is never author-owned. Authors supply tag strings and choose their layout position; the active User Tag profile always owns badge colors, borders, shape, typography, hierarchy, and animation. Source artwork must never imitate tag badges, authored Tag slots cannot override the profile, and a mismatch between source styling and User Tag rendering is not a conversion gap. Cost badges are a separate authored field.

Phase 5: extract and place images

Images preserve irreducible artwork, not authoring work. Before creating any crop that contains meaningful text, cost, rules, borders, or card composition, complete a semantic expressibility audit against the available section and choice layout nodes.

  1. Retain lossless full-page renders for verification.
  2. Crop only coherent graphical units that cannot reasonably be authored: emblem art, maps, individual sprites, character art, and textures. Record each crop's page and pixel bounds. A logo lockup containing authorable title, edition, or byline text must be split into live text plus its irreducible mark whenever the semantic workflow can express that composition.
  3. Rebuild labels, descriptions, rules, costs, separators, backgrounds, and card structure with live Text, Slot, Rule, Stack, Inline, Wrap, and Grid nodes wherever those primitives can express them.
  4. Split mixed source strips into artwork-only crops and live text. For example, crop the six Starting Kit sprites separately and author their labels and descriptions in a six-column grid.
  5. Remove neither attribution nor meaningful labels when the crop depends on them for interpretation.
  6. Use PNG for source raster art unless a supported lossless format provides a material size benefit. Do not trace source raster art into invented SVG.
  7. Provide concise semantic alternative text. Decorative layout backgrounds must still originate from a validated Image block, but are not announced twice.
  8. Check per-image, package-pixel, expanded-byte, and compression-ratio limits before polishing layouts.

Phase 6: reproduce layout and color

First create the machine-readable visual specification required by the visual-fidelity protocol. Measure aspect ratios, major bounds, typography hierarchy, art anchoring, gaps, rules, and occupied-to-empty-area ratio before choosing layouts. Then sample exact source colors and map them to semantic appearance roles. A page's color is not automatically a safe control or focus color; contrast diagnostics must remain clean.

  • Cluster repeated source cards into measured archetypes, then use section layouts for major hierarchy and choice layouts for the repeated anatomy.
  • Match silhouette and major bounds before hierarchy and styling. Do not substitute a conventional name/art/prose stack when the source is a horizontal strip or asymmetrical display composition.
  • Write the source and authored layout trees explicitly. If the source is Inline(Stack(Roll, Pay), WorldText), verify that exact parent-child structure in the rendered bounds and then inspect each child's internal distribution separately.
  • Create a relationship ledger for every repeated archetype. Record the source anchor for its name, body, artwork, cost, control, rules, color bands, and deliberate negative space; record which nodes share an edge or action cluster. Treat Cost and Control as first-class parts of that composition, never as fields to append after the prose is finished.
  • Measure Grid cells, direct placement boundaries, Choice articles, authored layout roots, and visible painted surfaces separately. Equal Grid cells do not prove that the visible cards stretch through every wrapper.
  • Use column-weight for measured integer track proportions, spans for source-authored wide cards, and grow for free-space distribution among direct Stack or Inline children. A content-length difference is not evidence that padding is missing, and equal outer Inline heights do not prove that a nested Stack distributes its children correctly.
  • Use padding-block/padding-inline, minimum dimensions, and aspect ratio only after measuring the relevant axis. Omission intentionally retains current intrinsic behavior.
  • Choose a shared text-size token when it closely fits the measured hierarchy. The same field accepts a bounded exact px/rem value when the source falls materially between tokens. Use approved system typography, hard breaks, and semantic-list presentation before declaring type or line composition blocked.
  • Map every source text block exactly once before polishing. Preserve casing, punctuation, heading/subheading distinction, entitlement lines, plus/minus meaning, and list-item boundaries. Do not collapse visibly distinct source lines into a paraphrased sentence merely because the facts survive.
  • Split visually separated paragraphs into separate Text nodes inside a Stack with a measured gap. Do not assume blank lines within one rich-text block will reproduce the source's paragraph rhythm.
  • Verify text alignment and wrapping independently: text-align: center proves centering, but a centered two-line render still fails a centered one-line source.
  • Place cost and action controls at the source's natural action edge. Re-measure after adding controls because an otherwise correct card can fail when a control rail changes its height.
  • Do not create an orphan action rail: a full-width or contrasting strip containing only a control is a failure unless the source contains that strip. Prefer an existing source-aligned corner, pair Cost and Control in the same compact cluster when the source leaves room, and keep equivalent neighboring cards on the same control grammar.
  • Choose control alignment from local visual continuity. Center a control only when the source content it completes establishes a centered axis; keep ordinary tile controls aligned to their own labeled action edge.
  • Make control-adornments explicit on every Control and Roll slot. In an additive facsimile rail, place the live Control, dynamic Cost, and effect Tags together whenever those values exist; source pixels containing a printed price do not replace the live fields.
  • When a text, select, or integer answer names an acquired record, interpolate that answer into the grant name and verify the projected Chain Tracker record. Declare a meaningful property when the grant-name interpolation scope requires one.
  • Treat crop edges as data. Record whether each edge owns a border, then reject accidental neighboring gutters, rules, and partial glyphs with an exact pixel-edge audit.
  • Evaluate contrast from the rendered foreground and nearest effective background, not from authored token names. Small text must reach 4.5:1 and qualifying large text 3:1. If an exact sampled accent is insufficient at the available size, increase hierarchy, add a source-coherent backplate, or record the typography limitation.
  • Test the longest unbreakable word and the densest prose block at every acceptance width. Reject clipping, horizontal overflow, stranded words, implausible line breaks, or a fallback typeface whose width and weight destroy the source hierarchy. A supported condensed family still needs an explicit measured weight and size.
  • Give every fallback control a visible adjacent label. Source text inside an image is not an accessible or spatially reliable label for a detached checkbox or radio.
  • Live semantic name, cost, artwork, prose, rules, and controls define the semantic workflow. A text-bearing facsimile defines a separate workflow and archive; it is never evidence that the semantic workflow exhausted the syntax.
  • Use existing direct Choice and direct source-member associations when a source requires explicit cell placement. Use expand for repeated source order when that order already matches the source; do not report direct member placement as missing.
  • Use rules, backgrounds, borders, axis spacing, growth, weighted tracks, spans, bounded geometry, typography, hard breaks, list presentation, compact interaction slots, and image sizing before declaring a gap. Preserve verified artwork and transcription while making the smallest targeted correction, then cite the exact schema or renderer constraint for anything still blocked.

Presentation variants

The caller chooses the workflow. When both are requested, build two ordinary, independent .jmp archives rather than adding application profiles or blending their claims:

  • Semantic workflow: live reflowable text, live costs and controls, artwork-only crops, and the closest declarative layout.
  • Facsimile workflow: measured source panels for pixel reference, backed by the same semantic Choice data and clearly marked accessibility and dynamic-state limitations.

This distinction belongs to the conversion process only and must not leak into Format 1 or the application as modes, profiles, preferences, or package metadata. Evaluate each requested archive against its own contract. The facsimile workflow preserves the successful measured-panel process; the semantic workflow must exhaust valid syntax before rasterizing text or card composition.

Unsupported-mechanics policy

Never counterfeit a source rule. Use the nearest valid control, preserve source prose and base values, and attach a stable gap ID.

Conversion ledger contract

The ledger is working data, not a second Jump definition. Each entry records a stable ID, source page and pixel bounds, transcription status, target file and handles, semantic kinds, tags, fidelity result, and gap IDs. Its top level records source authority, page geometry, policy, gap definitions, and verification results.

{
  "id": "choice:example",
  "source": { "page": 4, "bounds": [0, 255, 1920, 300] },
  "transcription": { "status": "verified", "authority": "supplied-pdf" },
  "target": { "file": "choices.jdef", "handles": ["example"] },
  "tags": ["survival"],
  "fidelity": "transparent-approximation",
  "gaps": ["GAP-001"]
}

Verification and acceptance

  1. Canonicalize using the distribution profile and the exact asset path set. Resolve every error and warning.
  2. Build the archive and inspect it through the secure package import service. Require ready, not a partially reviewed hand-built ZIP.
  3. Import through the real Editor UI and inspect every section at desktop and narrow viewport widths, plus a narrow Editor preview inside a wide application window. Responsive evidence follows the rendered Jump container, not only the browser viewport.
  4. Exercise every distinct mechanic: manual and rolled selection, continuity, optional single and bounded multi groups, text/select/integer controls, flat and repeated costs, discount policies, locks, Jump grants, properties, every grant kind, and ownership targets.
  5. Apply the FAC-001 through FAC-006 interactive facsimile checks: relationship-specific alignment, explicit adornment suppression, projected dynamic names, complete live action rails, clean crop edges, and labeled option controls.
  6. Capture rendered evidence after images settle. Compare every archetype to its source at equal content width.
  7. Capture each interactive archetype in its materially different states: unset, selected, disabled, rolled when applicable, and at a source maximum. Selection state must not unexpectedly change card widths, action-cluster bounds, backgrounds, or neighboring alignment.
  8. For every repeated-card group, capture the entire group and deterministically sample inter-card gutters. Isolated card captures cannot prove separation, parent-surface ownership, or group rhythm.
  9. Run an automated crop-edge audit over all artwork-only assets and a rendered contrast audit over every authored text block. These are rejection gates, not substitutes for direct image comparison.
  10. Require aspect ratio and major bounds within 10%, matching direction, art anchoring, casing, hierarchy, line count, paragraph gaps, exact palette, and no large unmatched whitespace. Controls must not silently displace the composition.
  11. Capture a bounds-visible rendering and verify the actual layout tree, equal cross-axis bounds for stretched Inline children, stretched Grid card surfaces, proportional allocation, spans, and internal Stack distribution. Do not infer structure solely from where glyphs end.
  12. For every source-authored horizontal sequence, measure every direct child's row position at comparison width and assert that the renderer itself has no horizontal overflow. A cropped or horizontally displaced viewport can imitate wrapping; distinguish scroll displacement from an actual row break before changing structure.
  13. List the five largest perceptual differences, fix every authoring defect, and label each residual difference blocked with the exact missing capability. When an artifact disagrees with expected behavior, trust the artifact and continue.
  14. Run the adversarial glance audit: ask whether anything clips, truncates, inverts a source color band, moves a rule to the wrong relationship, merges distinct cards, creates an orphan rail, misanchors Cost or Control, introduces uneven rhythm, or changes geometry after interaction. Any “yes” is a blocking failure, even when all numeric assertions pass.
  15. Verify painted relationships, not only node order. When the source specifies text → rule → text, measure the visible surfaces: the first text surface must end where the rule begins and the second must begin where the rule ends. Parent padding, gaps, or backgrounds must not turn a thin rule into a wider color band.
  16. Audit repeated cards as a group, not only as isolated cards. Sample every horizontal and vertical gutter, compare it with the source gutter color, and verify that each card owns a distinct painted surface. A correct card on a wrong parent background is still a failed composition.
  17. Scan every card edge for painted containment, including pseudo-elements such as list markers. DOM overflow metrics do not account for every painted marker; require each marker's logical start edge to remain inside the card's inner border and keep every gutter free of foreground paint.
  18. Maintain a source-style ledger for each text role—family class, weight, size, line height, casing, and color—and inspect computed renderer values. Presence and approximate size do not excuse substituting regular text where the source uses a heavy condensed face.
  19. Update ledger verification only after the exact path passes. Leave known gaps open and named.

Handoff checklist

  • Original source remains unchanged and ignored.
  • Every source block has a ledger entry and a second transcription pass.
  • Every visible source node has exactly one disposition: live authored node, irreducible artwork crop, intentionally additive application control, or demonstrated gap.
  • Every referenced image exists, validates, and has appropriate alternative text.
  • Definition diagnostics and secure archive diagnostics are empty.
  • The built .jmp imports and exercises successfully.
  • Equal-width visual evidence covers every source page and every card archetype, with an explicit pass, fail, or blocked result.
  • Known gaps appear in both the ledger and a persistent audit when they reveal reusable format limitations.
  • No scratch source, extracted asset, or converted archive enters the repository commit.
