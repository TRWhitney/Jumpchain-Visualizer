Required conversion gate

Visual Fidelity for Autonomous PDF-to-.jmp Conversion

The instructions and evidence an agent needs to reproduce a source composition without a human having to notice that the result is visibly wrong.

Decision: visual similarity is a completion requirement, not a preference. A valid archive with accurate prose is still a failed conversion when the rendered composition does not resemble the source.

Why the first Pokémon pass failed

The first pass treated a Region as a generic responsive card. The source treated it as a tightly measured horizontal display strip. That was an implementation and review failure before it was a format limitation.

Required source measurements

Do not author a layout until the source has a machine-readable visual specification. Measure the following in source pixels and normalized percentages so the same specification works at another render width:

  • page and panel aspect ratios;
  • major bounding boxes for title, prose, art, price, separators, and intentional empty space;
  • layout direction, column count, unequal column proportions, row spans, and overlap;
  • art dimensions, crop, alignment, and distance from each edge;
  • text casing, alignment, line count, relative size, weight, condensation, line spacing, paragraph grouping, and inter-paragraph gaps;
  • palette sampled from the source rather than estimated;
  • border width, gutters, card gaps, corner geometry, and occupied-to-empty-area ratio;
  • the natural position and footprint of interactive controls that must be added.

Also create a source-node inventory: every visible heading, subheading, side note, prose block, list line, price, rule, artwork unit, and deliberate empty region receives coordinates and one planned disposition. Cluster repeated measurements into named visual archetypes—such as horizontal region strip, two-column skill card, or charcoal flaw row—and define one reusable layout per archetype. Generic cards are prohibited until this clustering is complete.

Implementation order

  1. Write both layout trees. Express the source and proposed Format 1 composition in compact notation such as Inline(Stack(Roll, Pay), WorldText). Every source sibling relationship must have an explicit authored counterpart.
  2. Reconstruct the source silhouette. Match aspect ratio, direction, column proportions, and art anchoring before styling text.
  3. Reconstruct hierarchy. Match display-name dominance, casing, line breaks, price emphasis, and description density.
  4. Apply exact visual tokens. Use sampled colors, measured rules, square or rounded geometry, and measured gaps.
  5. Add interaction without redesigning the source. Put controls at an existing action edge, in an existing reserved region, or in the smallest clearly additive rail. Re-run the geometry checks after controls are present.
  6. Audit semantic expressibility before any text-bearing crop in the semantic workflow. Decompose the panel into Stack, Inline, Wrap, Grid, horizontal or vertical Rule, Text, Slot, Input, and artwork-only Image nodes. Record which exact primitive blocks each remaining difference.
  7. Keep facsimile and semantic output as caller-selected workflows. A cropped source panel may preserve exact typography and composition in an ordinary facsimile archive. It neither replaces nor weakens a requested semantic attempt. Record its accessibility, reflow, rights, and dynamic-state losses.

Content fidelity includes visual grammar. A source plus/minus pair is not one summary sentence; three source equipment lines are not one prose paragraph; a main Future heading and its subheading are not interchangeable. Preserve those boundaries as separate Text targets or rich-text blocks before evaluating typography. Do not insert converter notes into the rendered Jump to explain an unsupported mechanic when the source wording already states the rule.

A matching tree is necessary but not sufficient. For example, Inline child boundaries may have equal heights while the text inside one child ends much earlier. Verify outer child bounds, then separately verify each child's internal alignment, distribution, wrapping, and occupied area. Do not infer the DOM relationship from glyph extents in a screenshot.

For every Grid comparison, measure four boundaries independently: the Grid cell, the direct layout placement, the Choice article, and the authored root or other visible painted surface. A corrected cell height is still a failure when an intermediate wrapper leaves the cyan or charcoal card shorter. Explicit Start, Center, and End are different: they are intentionally content-sized and must visibly reposition whenever free space exists.

When the source uses unequal regions, try proportional column-weight tracks before nesting or cropping. Use child spans for cards that cross tracks and direct-child grow weights for Stack/Inline free-space distribution. Verify a nested Stack’s children separately: equal outer Inline height does not establish that “Roll” and “Pay” received equal vertical allocations. At narrow width, verify that weights and spans collapse without horizontal overflow.

Typography follows the same minimal-experiment rule. Try the strengthened shared text scale first, then a bounded exact value in the same text-size field, approved system family/weight/line metrics, explicit hard breaks, and semantic list presentation. Exact identity of an unavailable source font is a genuine limitation; ordinary heading scale, tracking, line height, hyphen markers, and measured breaks are not.

Likewise, a computed text-align: center value does not prove visible centering. Measure the rendered glyph center against the intended card or column center and confirm that the text boundary occupies the intended width. The Pokémon conversion exposed a global 72ch prose cap that made the property technically correct while the result remained visibly left-biased.

Use multiple Text nodes inside a Stack when the source has visually separated paragraphs. Blank lines inside one rich-text value preserve semantic paragraphs but do not provide authored inter-paragraph spacing. Give the Stack the measured gap.

A facsimile is a transparent conversion workflow, not evidence that the format can semantically express the design. The underlying Choice must retain verified name, description, cost, tags, and grants. The crop needs meaningful alternative text, and the ledger must identify its source coordinates. The separately built semantic archive must not reference the text-bearing crop.

Interactive facsimile acceptance contract

A source crop can make a card look correct while its additive interaction remains obviously unfinished. Review each live action rail as part of the composition and require the following observable checks:

These checks are conversion requirements, not new Format 1 gaps. A gap is recorded only after the smallest valid syntax experiment fails. Centered Control slots, unadorned controls, live Cost slots, User-profile Tag slots, interpolated acquired-record names, clean crops, vertical rules, Jump grants, and labeled mechanical rows are currently authorable. Final-decision columns need no control alignment because the conversion must not create those controls.

Hard visual acceptance gate

Compare source and rendered artifacts at the same content width. Each archetype receives an explicit pass, fail, or blocked result; “recognizable” is not a result.

  • overall and card aspect ratios differ by no more than 10% unless a named control rail explains the additional dimension;
  • major title, prose, artwork, price, and rule bounds are within 10% of their source positions and dimensions;
  • every claimed Stack, Inline, Wrap, or Grid relationship is verified against the rendered layout tree; direct Inline child boundaries have equal cross-axis extent when stretch-aligned, and stretched Grid cells, placement boundaries, articles, authored roots, and visible surfaces end within one CSS pixel;
  • paragraph gaps, sibling gaps, internal Stack distribution, text alignment, and line wrapping match independently of the outer panel aspect ratio;
  • layout direction, art edge anchoring, casing, dominant type hierarchy, and description line count match;
  • the exact sampled palette is used;
  • every text run meets 4.5:1 contrast, or 3:1 only when its computed size and weight qualify as large text, against its effective rendered background;
  • artwork-only crops own all four edges and contain no adjacent rule, gutter, border, or partial glyph;
  • no large unmatched whitespace appears;
  • controls do not displace, cover, or reorder source content without a recorded gap;
  • no full-width or contrasting orphan action rail appears unless the source has the same band; Cost and Control use the source's available edge or a deliberately measured additive cluster;
  • the longest word and densest text block remain inside their bounds at desktop, tablet, phone, and narrow embedded-preview widths without clipping, horizontal overflow, or a hierarchy-breaking wrap;
  • unset, selected, disabled, rolled, and at-limit states preserve card and action-cluster geometry unless the source or application status region deliberately reserves that change;
  • the side-by-side pair reads as the same composition at a glance.

Thresholds are necessary but not sufficient. A renderer can satisfy an aspect ratio while moving the map, shrinking the name, or losing the hierarchy. The final glance comparison remains mandatory.

Adversarial glance questions

The reviewing agent must answer every question from the rendered screenshot, at readable scale, rather than from markup or intended behavior. One affirmative answer blocks completion:

  • Does any text clip, overflow, truncate, strand a word, or wrap into a visibly worse hierarchy than the source?
  • Is any source foreground/background relationship inverted, any rule attached to the wrong pair of blocks, or any distinct source card merged into an undifferentiated band?
  • Does a Cost or Control sit in a generic corner or rail instead of the source's available anchor? Does a control-only strip exist without a source counterpart?
  • Do neighboring cards that serve the same function use visibly different control spacing, alignment, density, or action-cluster anatomy?
  • Are list items, paragraphs, or card interiors too loose or too cramped compared with the source?
  • Does selecting, disabling, rolling, or reaching a maximum resize an action region or disturb neighboring geometry?
  • Even if the measurements pass, is there any jarring artifact that would be obvious in an equal-width side-by-side comparison?

Iteration and evidence loop

  1. Capture the source panel and rendered panel at equal width.
  2. List the five largest visible differences, ordered by perceptual impact.
  3. Classify each difference as an authoring defect or a demonstrated format gap. Default to authoring defect until a minimal syntax experiment proves otherwise.
  4. Fix authoring defects and capture again. Never stop merely because a test is green.
  5. For a format gap, cite the exact schema or renderer constraint and preserve a minimal reproducer.
  6. Retain source crops, screenshots, measured geometry, and the pass/fail/blocked record in ignored scratch evidence.

The screenshot is the authority for a visual claim. If implementation reasoning says the layout should match but the screenshot does not, trust the screenshot and continue.

Independent visual critic

When subagents are available, assign a critic that did not author the conversion. Give it only the source crop, rendered crop, measurement specification, and acceptance rubric. Ask it to return:

  • pass, fail, or blocked for each acceptance check;
  • the five largest perceptual differences;
  • whether each difference is actually prevented by Format 1;
  • the next highest-value change, without editing the project.

The primary agent remains responsible for checking the critic's claims against the schema and for iterating. A critic does not replace direct visual inspection.

Blocked versus complete

If the requested fidelity requires capabilities outside the authorized task, stop calling the conversion complete. Report the exact blocked property—for example, “controls cannot overlay an image or reserve absolute coordinates”—and present the best safe fallback. The developer must be able to distinguish:

  • semantic match: the renderer recreates the source with live text and layouts;
  • facsimile match: a separately built ordinary archive preserves source pixels while live controls remain additive;
  • approximation: the composition differs but preserves selected visual tokens;
  • blocked: an acceptance criterion cannot be met without a format or renderer change.

Reusable agent prompt

Treat visual similarity as a completion requirement.

Before authoring:
1. Render every source page losslessly.
2. Produce a machine-readable visual specification with page/card bounds,
   normalized proportions, aspect ratios, typography hierarchy, palette,
   art anchoring, borders, sibling and paragraph gaps, whitespace ratio, and
   control locations.
   Inventory every visible heading, side note, prose/list line, price, rule,
   artwork unit, and deliberate empty region exactly once.
3. Cluster repeated cards into visual archetypes. Do not use a generic card
   layout until the archetypes are identified.
4. Write the source layout tree and proposed Format 1 tree for every panel.
   Map every source node to a live Text, Rule, Stack, Inline, Wrap, Grid, Slot,
   Input, or artwork-only Image node.
   For each repeated card, also record the anchors and shared edges of its name,
   body, art, Cost, Control, rules, color bands, and intentional negative space.

During authoring:
5. Match silhouette and major bounds first, hierarchy second, styling third.
6. Keep interactive controls additive and at a natural source action edge.
   Align each control to the local source-content axis; do not center controls
   globally. Make every Control/Roll adornment setting explicit.
   Never append a generic control-only rail. Use a source-reserved edge or the
   smallest measured Cost/Control cluster, and use one control grammar for
   neighboring cards with the same role.
7. Keep semantic text, costs, tags, grants, rules, and card structure live.
   Crop only irreducible artwork in the semantic workflow.
   Split title lockups into live title/edition/byline text and irreducible mark
   art whenever the syntax can express the composition.
   In facsimile action rails, include live Control, Cost, and effect Tags when
   available; printed pixels do not replace dynamic fields.
8. Represent visually separated paragraphs as separate Text nodes in a Stack
   with a measured gap. Match text alignment and source line count explicitly.
   Preserve headings, subheadings, plus/minus lines, entitlement lines, and
   list-item boundaries; do not paraphrase them into fewer blocks.
9. Build the caller-selected workflow. If both are requested, emit separate
   ordinary facsimile and semantic archives. Never add application profiles,
   and never use facsimile evidence to bypass semantic layout work.

Verification:
10. Capture source and render at equal width for every archetype, once normally
    and once with rendered layout bounds visible. Capture interactive archetypes
    unset, selected, disabled, rolled when applicable, and at their maximum.
11. Verify every claimed parent-child relationship. For each Inline, measure
    direct-child cross-axis bounds, width allocation, internal alignment, and
    occupied content area separately. Equal outer heights do not prove matching
    internal distribution.
12. Require aspect ratio and major bounds within 10%, matching layout direction,
   art anchoring, casing, hierarchy, line count, palette, and no unmatched
   whitespace.
   Reject anonymous mechanical option controls, generic acquired-record names that omit a
   user-entered identity, unexpected control adornments, hidden action metadata,
   and crops containing adjacent gutters or rules.
   Compute actual foreground/background contrast for every authored text block
   and fail small text below 4.5:1 or qualifying large text below 3:1.
   Test the longest unbreakable word and densest prose at desktop, tablet, phone,
   and narrow embedded-preview widths. Reject clipping, overflow, hierarchy-breaking wraps, orphan
   action rails, misplaced costs or controls, loose list rhythm, inverted color
   bands, misplaced rules, merged cards, and interaction-driven geometry changes.
   Node order is not evidence of visual adjacency. For every rule that separates
   painted surfaces, measure both neighboring surface edges and the rule thickness;
   reject any parent gap, padding, or background that widens the rule into a band.
   An isolated card is not evidence for a repeated-card layout. Capture the whole
   group, sample every row and column gutter, and reject a parent background that
   merges distinct source cards into a single field. Record the computed family,
   weight, size, line height, casing, and color for each source text role; do not
   accept regular text where the source role is heavy and condensed.
   Scan the complete painted edge of every card, including pseudo-elements. A
   passing scroll-width check does not prove that an outside list marker remains
   inside the border. Reject any marker, glyph, badge, control, or artwork pixel
   that crosses an owned border or enters a gutter without matching source evidence.
   Reproduce final Home/Stay/Next-Jump choices as prose and visuals only.
13. List and fix the five largest visible differences. Treat each as an
    authoring defect until a minimal syntax experiment demonstrates otherwise.
    Answer every adversarial glance question from the screenshot at readable
    scale. Any jarring artifact blocks completion. Repeat until each check passes
    or is demonstrably blocked by the format.
14. If blocked, cite the exact missing capability and do not label the visual
    conversion complete. Preserve screenshots and measurements as evidence.

Use an independent visual critic when available. Trust the rendered artifact
over implementation intent.

Script and future skill boundary

A reusable conversion skill should package deterministic scripts for page rendering, crop generation, color sampling, geometry extraction, contact sheets, equal-width screenshots, aspect/bounds checks, pixel or perceptual comparisons, ledger generation, archive building, and secure import verification. The skill instructions should own the decision gates; scripts should collect evidence and perform mechanical work rather than decide that a composition “looks close.”

The Pokémon tightening pass adds four mandatory script contracts. Each command exits nonzero on failure and writes its measurements to the ignored ledger or verification directory:

  • Layout lint: enumerate every Control and Roll slot, require an explicit adornment value, require named facsimile option rows, and require Control, Cost, and Tags targets for each archetype that declares those live fields.
  • Crop audit: reproduce every asset byte-for-byte from its declared page coordinates, check intended ownership for all four edges, and reject full-edge neighboring gutters, rules, or borders. Artwork-only and facsimile crops use separate output destinations so regeneration cannot pollute the semantic archive.
  • Projection audit: enter distinctive text/select/integer values, evaluate the built package, and verify names, descriptions, ownership, quantity or rank, and companion/form targets exactly as the Chain Tracker will consume them.
  • Rendered interaction audit: import through the real package review path; measure relationship-specific control alignment; assert zero unexpected adorned boundaries; prove live tags and costs are visible beside their controls; and capture labeled fallback rows and representative action rails.
  • Repeated-surface audit: capture each complete repeated-card group; sample every inter-card gutter and both neighboring card interiors; compare those colors with the source relationship ledger; and reject merged “seas” caused by a transparent Grid over the wrong parent background.
  • Painted-edge audit: scan all four card-edge bands at native scale, including marker and pseudo-element paint that DOM overflow dimensions can omit; report the exact card, edge, and offending pixel extent.
  • Typography-role audit: record computed family, weight, size, line height, casing, and color for every named text role and compare them with the measured source-style ledger. Visual intuition from the converting agent is supplementary evidence, never the sole pass condition.

Do not make the scripts silently “repair” ambiguous crops or alignment. They may generate candidate bounds and contact sheets, but the visual specification must record the selected edge ownership and alignment relationship explicitly.
