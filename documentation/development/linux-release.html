Maintainer playbook

Linux AppImage release

One local command verifies, builds, inspects, smoke-launches, and stages an unsigned x86-64 AppImage. Publication remains a deliberate human action.

Accepted release contract

  • The build host is x86-64 Ubuntu 22.04 or Debian 12. A newer distribution is rejected because its glibc can silently raise the minimum supported runtime.
  • The Git worktree is clean before and after verification. Release contents therefore correspond exactly to one commit.
  • Node, Cargo, and Tauri metadata agree on version, license, publisher, repository, and stable application identifier.
  • The artifact is an unsigned AppImage. No key, certificate, upload credential, or public release service participates in the command.
  • The embedded WebDriver plugin remains debug-only. Release binaries never expose the test driver.

One-time host setup

The repository pins Rust 1.97 with the required formatting and lint components. Rustup installs that toolchain automatically when it is absent. Run pnpm setup:release:linux once; it installs the pinned tauri-driver through Cargo when absent. If WebKitWebDriver is not installed system-wide, it downloads the signed distribution package without root access and extracts the driver under the ignored target/release-tools directory. A later explicit Cargo clean may remove that local copy; the setup command recreates it.

Create a candidate

corepack pnpm release:linux

The command runs pnpm check:release, removes inherited Windows directories from the packaging child process’s PATH, builds with Tauri’s noninteractive --bundles appimage --ci --no-sign options, and requires exactly one artifact for the declared version. Native verification packages and drives an optimized AppImage with a test-only WebDriver feature under temporary XDG data, config, and cache directories so test-created workspaces never enter the developer profile; publication builds omit that feature. The release packager removes linuxdeploy’s fixed GTK_THEME and X11 backend overrides so the application can use the native display backend and switch GTK window chrome and native dialogs between Light and Dark at runtime. It extracts the final AppImage and verifies that theme contract, its x86-64 ELF executable, desktop metadata, icons, and byte-identical project and third-party license files. It then launches the exact AppImage with isolated XDG data directories and requires the process to remain healthy through the startup window.

Publication-ready output is written to target/release-artifacts/<version>. It contains the normalized AppImage filename, a source archive from the same Git commit, a JSON manifest, and SHA256SUMS. Re-running the same clean commit atomically replaces only that generated version directory.

Inspect an existing AppImage

corepack pnpm inspect:appimage -- path/to/application.AppImage

This performs extraction, content validation, and the isolated launch smoke without running the full release gate or producing publication files.

Manual acceptance before publication

Automation cannot substitute for a native desktop compatibility check. The generated candidate is technically complete; the following human acceptance and publication work remains for every public AppImage release.

  1. Confirm that the staged version is the intended public version and that the manifest names the exact commit being released.
  2. Verify SHA256SUMS, then run the staged AppImage on one clean Ubuntu 22.04 installation and one current non-Debian distribution such as Fedora. Testing a developer workstation alone is not sufficient.
  3. On each distribution, verify first launch and onboarding, Light and Dark native chrome, the Author Reference pattern tester, native open/save dialogs, screen eyedropper success/cancel/portal-rejection behavior, persistence across relaunch, absence of unexpected Untitled Jump workspaces, package import/export, and clean exit.
  4. Write release notes that record the exact tested distributions, the x86-64 and unsigned-package scope, the Ubuntu 22.04/glibc 2.35 compatibility baseline, the lack of an automatic updater, known WSL limitations, and the command needed to mark a downloaded AppImage executable.
  5. Create the version tag only after manual acceptance. Publish the staged AppImage, source archive, manifest, and SHA256SUMS together.
  6. Download the published files through the same public path a user receives, verify their hashes again, and perform one final launch.

Deferred Linux polish

AppStream metadata may be added later to improve presentation in AppImageHub and software catalogues and to remove the current packager warning. It is not required for direct AppImage execution. GPG signing is also optional and is not part of the accepted unsigned release contract; the checksum file remains an integrity aid rather than independent proof of publisher identity.

Publication boundary

The release command never creates a tag, changes a version, writes release notes, uploads files, or contacts a hosting API. After manual acceptance, publish the staged AppImage, source archive, manifest, checksum file, and human-written release notes through the chosen project host.

Other desktop targets

Windows and macOS packaging have not been implemented yet. Their accepted implementation and acceptance sequences are maintained in the Windows release roadmap and macOS release roadmap.
