macOS release roadmap

macOS follows Windows and must be built and accepted on Apple hardware. The repository has shared application metadata and an ICNS icon, but no macOS-specific packaging, inspection, native-test, or staging workflow exists yet.

Proposed release contract

  • Build on a clean Mac using a current Xcode toolchain, pinned Node 24, pinned Rust, and both Apple Rust targets.
  • Ship one universal DMG containing a universal application bundle for Apple Silicon and Intel. Direct download is the first distribution path; do not target the Mac App Store.
  • Choose and encode an explicit minimum macOS version only after compatibility testing. Do not accidentally claim Tauri's broad default minimum of macOS 10.13.
  • Retain dev.jumpchainvisualizer.desktop as the stable bundle identifier and include byte-identical UNLICENSE.md and THIRD_PARTY_NOTICES.txt resources.
  • Publish the DMG, source archive, JSON manifest, and SHA256SUMS together. Do not add an automatic updater in the first release.

Signing and Gatekeeper decision

macOS does not offer a low-friction unsigned direct-download path equivalent to Linux. Tauri documents code signing as necessary to avoid a browser-downloaded application being reported as unverified or broken. Apple notarization requires a valid Developer ID signature; an ad-hoc or self-signed identity cannot be notarized. See Tauri's macOS signing guide, Apple's Developer ID guidance, and Apple's notarization requirements.

If the project retains its no-public-signing-authority policy, configure Tauri's ad-hoc identity -. This satisfies the code-signature requirement of Apple Silicon binaries but does not establish publisher identity, cannot be notarized, and does not stop Gatekeeper from requiring the user to approve the application in Privacy & Security. Some managed Macs may prohibit that approval. Release notes must describe this as a supported-distribution limitation, and compatibility acceptance must exercise a genuinely quarantined download rather than only the local build output.

If ordinary click-to-open installation becomes a requirement, the remaining path is Apple Developer Program membership, a Developer ID Application certificate, Hardened Runtime, notarization, and a stapled ticket. That would be a policy change and is not assumed by this roadmap.

Decisions to close before implementation

  1. Confirm universal Apple Silicon plus Intel support rather than Apple-Silicon-only distribution.
  2. Select the oldest macOS release the project will support. Use a version still suitable for the application's WebKit and native API behavior, encode it with bundle.macOS.minimumSystemVersion, and test that exact floor. Tauri exposes the setting in its application-bundle guide.
  3. Confirm ad-hoc signing and its Gatekeeper friction, or explicitly reverse the signing policy and adopt Developer ID notarization.
  4. Audit required entitlements and Info.plist usage descriptions. Add only capabilities the app actually uses; native file dialogs alone do not justify App Sandbox adoption.
  5. Decide whether Finder/Info.plist strings need platform localization in the first macOS release. Platform metadata localization is separate from in-app localization.

Implementation sequence

  1. Provision a real Mac build host with current Xcode command-line tools. Install the aarch64-apple-darwin and x86_64-apple-darwin Rust targets and prove the pinned toolchain builds both slices.
  2. Add a macOS-specific Tauri configuration selecting DMG, the universal target, the agreed minimum system version, ad-hoc signing identity or Developer ID identity, and any audited entitlements or Info.plist values.
  3. Add setup:release:macos, inspect:macos, and release:macos commands. They must reject non-macOS hosts, unsupported architectures, dirty worktrees, metadata drift, missing signing policy, and incomplete universal binaries.
  4. Extend native verification to drive a packaged macOS application under isolated data directories. The WebDriver plugin must remain test-only and be absent from the publication application.
  5. Inspect the mounted DMG and application bundle: verify both Mach-O architecture slices, bundle identifier and version, minimum system version, icon, exact license and notice resources, expected signature class, absence of test hooks, and consistent product metadata.
  6. For ad-hoc output, run strict local code-signature verification and document that it is not publisher authentication. For Developer ID output, enable Hardened Runtime, submit with notarytool, inspect the notarization log, staple the ticket, and assess the final DMG with Gatekeeper.
  7. Run the shared release gate and launch-smoke the exact packaged application. Exercise CodeMirror layout, native Light and Dark appearance, color controls, Author Reference compact popovers, persistence, and clean shutdown.
  8. Stage a normalized DMG filename, source archive from the same commit, platform manifest, and deterministic checksums. Add script tests for host and architecture rejection, universal-slice inspection, signature policy, metadata, resources, manifest rendering, and atomic staging.

Manual acceptance

  1. Test the universal candidate on a clean Apple Silicon Mac and a real Intel Mac at the claimed minimum or oldest available supported macOS version. Rosetta is useful additional evidence but does not replace Intel-hardware acceptance for an Intel support claim.
  2. Upload and redownload the DMG so it receives normal quarantine metadata. Verify SHA256SUMS, mount it, drag the app to Applications, and record the exact Gatekeeper flow. Confirm that the documented approval path works under the accepted signing policy.
  3. Verify first launch and onboarding, native open/save dialogs, Light and Dark mode, color picker and eyedropper success/cancel/permission-denial behavior, Author Reference tools, package import/export, persistence across quit and relaunch, absence of unexpected Untitled Jump workspaces, and clean quit.
  4. Verify display scaling on Retina hardware, keyboard shortcuts using Command, window restoration, Finder application metadata, and behavior when the DMG is ejected after installation.
  5. Write release notes that state tested hardware and macOS versions, universal architecture, minimum system version, signing/notarization status, Gatekeeper instructions, and lack of automatic updates. Tag only after acceptance, publish all staged files together, redownload, verify hashes, and perform one final installation.

Deferred alternatives

Mac App Store distribution, Apple-Silicon-only packaging, separate per-architecture DMGs, automatic updates, and Developer ID notarization remain explicit future choices. They must not be mixed into the first macOS implementation without updating this release contract.
