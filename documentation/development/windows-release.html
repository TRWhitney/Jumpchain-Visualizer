Planned maintainer playbook

Windows release roadmap

Windows is the next packaging target. The repository has shared application metadata and a Windows icon, but it does not yet have a Windows-specific build, inspection, native-test, or staging workflow.

Proposed release contract

  • Build on a clean x86-64 Windows host using the pinned Node 24 and Rust toolchains plus the Microsoft C++ build tools.
  • Ship one x86-64 per-user NSIS setup executable as a direct download. Do not add MSI or Microsoft Store distribution to the first Windows release.
  • Support Windows 11 x64. Treat Windows 10 as unclaimed best-effort compatibility unless it receives a deliberate support decision and the same manual acceptance coverage.
  • Remain unsigned unless the project later adopts a trusted signing service or Microsoft Store distribution. Signing policy must not be silently changed by release automation.
  • Retain dev.jumpchainvisualizer.desktop as the stable application identity and bundle byte-identical UNLICENSE.md and THIRD_PARTY_NOTICES.txt.
  • Publish the installer, source archive, JSON manifest, and SHA256SUMS together. Do not add an automatic updater in the first release.

Unsigned Windows consequence

Unsigned executables may show Windows protected your PC. Microsoft states that an unsigned file starts with no transferable publisher reputation for every new version, a self-signed certificate behaves like no signature, and organizational policy or Windows 11 Smart App Control may prevent users from bypassing the block. Release notes and download instructions must state this plainly and provide the published SHA-256 value, but a checksum hosted beside the installer is not a substitute for trusted publisher identity. See Microsoft's current SmartScreen guidance.

Decisions to close before implementation

  1. Confirm NSIS per-user installation and the Windows 11 x64 support baseline.
  2. Choose WebView2 installation mode. The recommended first choice is Tauri's embedded Evergreen bootstrapper: it adds roughly 1.8 MB and covers machines missing WebView2, but initial installation requires network access. A fully offline installer adds roughly 127 MB. Skipping the check creates a known failure mode on machines without the runtime. Windows 11 includes the Evergreen runtime, while Microsoft still recommends covering edge cases. See the Tauri Windows installer guide and Microsoft WebView2 distribution guidance.
  3. Decide whether the installer itself remains English-only for the first release or receives the supported application locales. Installer localization is separate from in-app localization.
  4. Define uninstall behavior for durable user projects and settings. The uninstaller must never delete external canonical project folders; retained application data must be disclosed.

Implementation sequence

  1. Add a Windows-specific Tauri configuration that selects only NSIS, sets the agreed install mode and WebView2 policy, and preserves shared product identity, icons, descriptions, license, and notices.
  2. Add setup:release:windows, inspect:windows, and release:windows commands. They must reject the wrong host or architecture, require a clean worktree, enforce synchronized versions and metadata, and use noninteractive tooling.
  3. Extend native verification to drive a packaged Windows candidate rather than only a development binary. Keep the WebDriver plugin test-only and prove that it is absent from the publication build.
  4. Inspect the installer and installed application for x86-64 PE executables, stable product and publisher metadata, the application icon, exact license and notice resources, and expected shortcuts. Verify installation and uninstall under a standard user without requiring administrator rights.
  5. Run the shared release gate, then install and launch the exact candidate with isolated test data. Exercise CodeMirror layout, Light and Dark chrome, the native color picker, Author Reference compact popovers, persistence, and clean shutdown.
  6. Stage a normalized installer filename, a source archive from the same commit, a platform manifest, and deterministic checksums under target/release-artifacts/<version>. Re-running a clean commit must atomically replace only that version's generated Windows directory.
  7. Add script-level tests for host rejection, artifact discovery, metadata and architecture checks, driver exclusion, manifest rendering, checksums, and staging behavior.

Manual acceptance

  1. Verify SHA256SUMS and test the downloaded installer on a clean, fully updated Windows 11 x64 account without development tools.
  2. Record the exact SmartScreen or Smart App Control experience. Confirm the documented path is actually available; do not claim that every policy permits an unsigned installer.
  3. Verify install, first launch, onboarding, Start-menu shortcut, open/save dialogs, scaling at 100% and 150%, Light and Dark mode, color picker and eyedropper, Author Reference tools, package import/export, persistence across relaunch, absence of unexpected Untitled Jump workspaces, and clean exit.
  4. Uninstall and confirm the agreed application-data behavior. Reinstall and verify that retained data is either restored or absent exactly as documented.
  5. Write release notes, create the version tag after acceptance, publish all staged files together, redownload them, verify hashes, and perform one final installation.

Deferred alternatives

MSI, Microsoft Store publication, ARM64, automatic updates, and trusted code signing remain separate future decisions. The Tauri installer documentation supports both NSIS and MSI, but carrying both formats would duplicate acceptance and support work without improving the first direct-download release.
