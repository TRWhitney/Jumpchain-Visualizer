Bundled external localization resources

Application-owned text is separated from behavior, while authored Jump and chain content keeps its original language and identity.

Decision

Use i18next with react-i18next. Vite eagerly discovers one folder per release-bundled language from src/localization/languages. Each folder contains a metadata manifest and feature-oriented message files. Browser and Tauri therefore use the same immutable resources; adding a language requires a rebuild. English is always present, starts first, is the default after reset, and is the per-key fallback for valid partial translations. Runtime user-installed packs are deferred.

// manifest.json
{
  "schemaVersion": 1,
  "languageTag": "en",
  "direction": "ltr"
}

// settings.json
{
  "settings": {
    "language": {
      "heading": "Language"
    }
  }
}

The folder name is the language's self-name. Tags must be canonical BCP 47 values and direction is either ltr or rtl. Folder names and tags must be unique. Message files are merged at build time and may be organized by feature, but no two files in one language may define the same leaf.

Language setting

Language is a native dropdown in the General Settings category. English appears first, followed by locale-sorted folder self-names whose options carry their own lang and dir. Selection rerenders immediately, persists as language.tag in settings schema 2, and updates the root document's language and direction. Invalid or unavailable persisted tags recover to English.

Translation boundary

Translate visible application chrome, accessible names, placeholders, tooltips, document and route titles, settings search terms, notifications, diagnostics, recovery copy, editor commands, Earth setup, supplement presentation, and built-in tag presentation. Keep stable IDs, persisted enum values, Format 1 keywords, file extensions, hashes, event/error codes, and canonical built-in matching terms invariant.

Do not translate imported or built-in Jump package prose, Editor-authored Jump content, user-supplied chain names and descriptions, story chapters, custom or acquired tag text, or test/review fixture prose. Supplement purchases and tag relationships remain keyed by stable IDs; a localized label must never change chain meaning.

Built-in tag IDs, canonical English names, and canonical aliases remain invariant. The active language supplies presentation labels and equivalent matching aliases at runtime. User-added aliases are layered beside those localized aliases and are never translated. If a user removes a built-in alias, its localized equivalent is also absent; switching language cannot restore it.

Context-menu actions follow the same boundary: reusable verbs are leaves in common.json, while object-specific accessible names and interpolated labels remain in application, Editor, Chain Tracker, tags, and Settings catalogues. Stable action IDs and domain command identifiers are never translated. Spanish and Arabic partial fixtures exercise fallback and right-to-left placement.

Validation and security

Catalogue validation is fail-closed: English must exist; schema, canonical tag, direction, size, depth, leaf count, file-name length, known keys, and interpolation/component tokens are checked. Translation strings are text, not trusted markup. Packs cannot provide arbitrary HTML, URLs, handlers, React props, or dangerouslySetInnerHTML. Rich messages may use only explicitly allowlisted Trans components. The AST audit rejects newly embedded production JSX, accessibility, placeholder, and notification display copy without interface-literal exceptions.

Contributor workflow

  1. Create a folder beside src/localization/languages/English and name it with the language's self-name.
  2. Copy manifest.json, set its metadata, then copy only the feature files and message leaves being translated. Missing files and leaves fall back to English.
  3. Keep the semantic English keys unchanged. Choose keys by feature and meaning, such as settingsSearch.language_tag.label, rather than source line, component position, or translated wording.
  4. Preserve every {{interpolation}}, plural suffix, and allowlisted component token exactly.
  5. Run formatter, unit and browser tests, Playwright, Rust checks, and a production build. Exercise the General language dropdown in both LTR and RTL directions.

Formatting, direction, and spell-check

Numbers, dates, lists, plural selection, case folding, and collation use the active BCP 47 tag. Layout uses document direction and logical CSS where direction matters. Natural-language authoring fields explicitly enable spellcheck; search, JSON, paths, handles, and CodeMirror source disable it. Native underlines still depend on the browser/webview and operating-system dictionary selected from the root lang.

English releases also bundle an offline Hunspell dictionary. It loads lazily only when an English language pack is active and supplies deterministic corrections when an author right-clicks a misspelled word in a Structured natural-language field. Suggestions replace only that word and preserve its capitalization. Interpolation handles inside {{…}} are excluded. Left click remains ordinary caret placement, and Shift+right-click requests the native editing menu. Other languages retain their native spell-check behavior until a compatible application dictionary is bundled. The application suggestion path performs no network lookup and does not send authored text away from the device.

Consequences and rejected alternatives

Bundling gives deterministic, offline behavior and one security model in browser and desktop, at the cost of requiring a release rebuild for a new language. Operating-system auto-selection was rejected so first launch remains predictable and English recovery is always available. Runtime pack installation was deferred because it would require signature, storage, update, and trust decisions beyond this foundation.
