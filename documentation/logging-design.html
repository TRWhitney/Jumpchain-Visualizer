Accepted direction

Logging design

A local-first, structured record of application behavior that helps diagnose failures without quietly becoming analytics, surveillance, or a second persistence model.

Status: logging direction settled. Logs exist only for the current application session, the complete viewer lives under Settings → Developer → Logs, crash reports include full application stack and environment details for reviewed Copy or Save workflows, and selected user-facing events may project to configurable toast notifications.

Purpose and Boundaries

Logging exists to explain what the application attempted, what failed, and which subsystem was involved. It does not establish user intent or authoritative chain state. Choices, grants, rolls, undo history, package snapshots, and autosave recovery remain in their owning domain stores.

Diagnostic log

Structured session events for troubleshooting parsing, storage, rendering, routing, and recovery.

Activity history

User-visible domain history such as reorders or removals. This belongs to chain/editor state and may reference a diagnostic correlation ID.

Telemetry

Transmission to a developer-controlled service. This is out of scope for the initial version and must never be implied by local logging.

Confirmed Principles

  • Use one application logging service rather than scattered production console calls.
  • Emit structured event records with stable event names and bounded attributes; prose is for display, not machine identity.
  • Logging must not be required for application correctness, undo, recovery, or security enforcement.
  • No event is transmitted automatically. Export is an explicit user action with a redaction preview.
  • Imported content is untrusted. Event names come from application code, while imported values are sanitized, length-limited attributes.
  • Failure to write a log must not recursively log or break the operation being observed.
  • A registered event may include user-notification metadata. The toast is a presentation of that event, not a second independently emitted event.

Structured Event Contract

The proposed record shape follows the general field separation used by the stable OpenTelemetry Logs Data Model without requiring an OpenTelemetry backend.

{
  "timestamp": "2026-07-10T18:42:31.442Z",
  "severity": "warn",
  "eventName": "logging.buffer.near_limit",
  "category": "logging",
  "sessionId": "session-scoped-random-id",
  "correlationId": "operation-scoped-random-id",
  "appVersion": "0.1.0",
  "routeKind": "chain",
  "attributes": {
    "usageBand": "high",
    "operation": "session-log"
  },
  "notification": {
    "class": "recovery",
    "messageKey": "logging.buffer.near_limit",
    "dedupeKey": "session-log-capacity"
  },
  "error": null
}
eventName
Stable dotted identifier selected from an application-owned catalog.
severity
debug, info, warn, error, or fatal.
sessionId
Random per-launch correlation value, never a user or installation identifier.
correlationId
Connects events produced by one import, save, render, or recovery operation.
attributes
Allowlisted scalar values with per-field type and length limits.
notification
Optional application-owned toast class, localized message key, and debounce/deduplication key.
error
Application error code, sanitized message, cause chain, and full application stack trace when an error exists.

Severity Semantics

  • Debug: detailed control-flow or performance context, disabled outside a temporary diagnostic session.
  • Info: expected lifecycle boundary such as startup completed or package validation completed.
  • Warn: recoverable degradation, blocked unsafe input, or state requiring attention.
  • Error: an operation failed and did not produce its intended result.
  • Fatal: the application cannot initialize or continue its durable workspace safely.

An allowed negative point balance is domain state, not automatically an error. A transition into or out of that state may emit a bounded informational event, while the authoritative signed balance remains in the chain entry.

User-Facing Toast Notifications

Some registered events carry notification metadata and may be projected as toasts. Every event still appears in the session log even when notifications are disabled globally or for its class. Toast settings affect presentation only.

Initial trigger classes are:

  • Action confirmations: explicit save, export, copy, add, remove, and reorder completion.
  • Editor activity: autosave, formatting, quick fixes, and preview recovery.
  • Chain activity: Jump changes, companion imports, supplement changes, rolls, and negative-balance transitions.
  • Validation: newly relevant diagnostics and blocked operations.
  • Errors and recovery: failed operations, permission loss, fallback recovery, and crashes.

The event catalog supplies a localized message key and stable dedupeKey. Input-driven notification candidates wait 500 ms after the last related input. Repeated events with the same class and dedupe key update the existing toast and increment its occurrence count instead of creating another toast. This debounce applies to toast presentation; diagnostic events may still be coalesced separately with their suppressed-event count.

  • The maximum-visible setting limits simultaneous toasts; additional toasts queue by severity and event time.
  • The duration setting applies after the latest coalesced update. Hover, keyboard focus, and pointer interaction pause dismissal.
  • Errors use an assertive announcement; other classes use a polite live region.
  • Closing a toast never clears or acknowledges the underlying log entry or diagnostic. An application-owned transient action, such as Undo, expires with the toast.
  • Disabling notifications immediately dismisses noninteractive toasts and stops new projections without disabling logging.

Privacy and Security Filter

The OWASP Logging Cheat Sheet recommends excluding secrets and treating personal data, file paths, and other identifiers carefully. It also calls for sanitizing untrusted event data to prevent log injection. For this application:

Never record

  • access tokens, permission handles, or credentials
  • raw Jump source, descriptions, images, or pasted content
  • chain, companion, author, or filesystem names
  • full filesystem paths or browser URLs with query/fragment data
  • complete exported chain or tag-profile documents

Record only in bounded form

  • application-owned error codes
  • line and column numbers without source excerpts
  • package hash prefixes or session-local pseudonyms
  • counts, duration bands, and storage-usage bands
  • sanitized browser/runtime capability names
  • Replace carriage returns, line feeds, control characters, and invalid Unicode before storage or display.
  • Reject unknown attribute keys at the logging boundary; do not serialize arbitrary objects.
  • Cap individual attribute values, event size, stack depth, and events per time window.
  • The viewer renders values as text only. Logged content never becomes HTML, Markdown, CSS, or a command.
  • Crash reports include complete application frames and cause chains. User-directory prefixes, filesystem paths outside the installed source tree, tokens, and imported values remain redacted.

Session Lifetime, Crashes, and Export

All diagnostic events live only in a bounded in-memory session buffer. Normal exit, restart, and process termination discard the buffer. Security and recovery events do not receive separate persistence.

  • The session ring retains at most 2,000 events or 10 MiB, whichever limit is reached first, and evicts the oldest low-severity events first.
  • Clear Session immediately discards the in-memory diagnostic buffer but not domain activity history.
  • Export creates versioned JSON Lines containing the current filtered or complete session after showing severity counts and redaction rules.
  • A caught unhandled exception opens a crash surface containing application/runtime/OS versions, architecture, route kind, relevant settings, the correlated session-event tail, the complete application stack and cause chain, and redaction notes.
  • The crash surface provides Copy Report and Save Report actions. Nothing is posted or transmitted automatically.
  • A hard native termination that prevents the crash surface from running may only reach the launcher or runtime standard-error output. The application documents this limitation rather than claiming guaranteed crash capture.
  • No background upload, beacon, remote crash report, protected security ring, or stable installation identifier exists.

Correlation and Failure Handling

One user operation receives one random correlation ID that follows parsing, validation, storage, and rendering events. This borrows the correlation principle standardized for distributed systems by W3C Trace Context without requiring network trace headers in a local-only application.

  • Logging writes are asynchronous and batched outside critical rendering input paths.
  • A saturated or unavailable session buffer emits at most one console-level emergency notice and never falls back to persistent storage.
  • Rate limits coalesce repeated identical failures and retain a suppressed-event count.
  • Fatal events attempt a final bounded write, but the recovery screen must not wait indefinitely for it.

Decision Record: Structured Session Logging

Status
Accepted
Context
The application needs useful failure evidence without a server dependency or accidental collection of private Jump and chain content.
Decision
Use a centralized structured logger and bounded in-memory session ring. Expose the full viewer under Settings → Developer → Logs. Include reviewed full application stacks and environment details in manual exports, but never persist or transmit logs automatically.
Consequences
Feature code uses registered event schemas; every launch starts with an empty log; recoverable crashes can produce useful copyable or saveable reports, while hard termination cannot guarantee an in-app report.

Settled Decisions

  • Every log class, including security and recovery, is session-only.
  • The complete viewer is a Logs subtab of the Developer category in Settings.
  • Reports contain full application stack traces and useful local environment/version information after privacy redaction.
  • Users can review, copy, and save diagnostic reports themselves.
  • No remote crash collection or separately protected security retention is planned.
  • Notification preferences change toast projection, not which events enter the session log.

Research References
