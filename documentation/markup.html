Language specification

Markup Design

Purpose

The live, export-clean coverage packages are catalogued in the Format 1 Demonstration Chain.

This document captures the agreed design direction for the jump authoring markup language and its package structure.

It is intentionally separate from ARCHITECTURE.md so markup decisions can evolve without turning the architecture document into a grab bag of unrelated details.

Design Goals

The markup language should solve the main authoring problems encountered with a JSON-based approach:

  • large files should remain readable by humans
  • nested structure should not require heavy bracket and comma management
  • prose-heavy content should be pleasant to write and review
  • syntax should stay regular enough for reliable tooling and validation
  • the language should not drift into a general-purpose programming language

The markup remains an authoring and interchange format, not the canonical in-memory model.

Current Direction

The current agreed direction is:

  • use a bespoke domain-specific markup language
  • favor indentation and keywords over JSON-style object/array literals
  • keep a small number of explicit syntax forms for clarity
  • use fenced rich-text bodies for prose content
  • use a rigid package structure instead of user-defined imports/includes
  • keep semantic declarations and presentation declarations separate

Syntax Principles

1. Indentation Plus Keywords

The language should be primarily indentation-based and declaration-oriented.

It should not feel like a generic serialized data dump. It should read like a structured document DSL.

The preferred shape is:

  • declarations begin with a keyword
  • fields use name: value
  • containment is indicated by indentation
  • repeated declarations are preferred over general-purpose inline arrays

2. Explicitness Where It Prevents Ambiguity

The language should reduce punctuation heavily, but not chase pure whitespace-only grammar.

Some explicit syntax is desirable to keep parsing and authoring unambiguous, especially for:

  • multiline rich text
  • nested declaration blocks
  • references
  • layout structures

3. Quoted Strings Are User-Facing Strings

Double-quoted scalar strings should be treated as user-facing/renderable string values rather than structural identifiers.

This gives the language a simple visual rule:

  • quoted strings are for user-facing text values
  • bare values are for structural identifiers and symbolic references

Quoted scalar strings support the escapes \", \\, \n, \r, and \t. Raw Unicode characters are valid directly. Any other escape sequence is an error. Authors should use the triple-quoted fenced form for multiline prose instead of constructing long bodies from escaped newlines.

A quoted scalar must open and close on the same physical line. Reaching the end of the line without a closing quote is a syntax error; Editor recovery remains limited to that line rather than consuming following declarations.

Examples of values that should stay bare:

  • handle
  • group
  • layout
  • source

This distinction makes the language easier to scan and gives placeholder interpolation a clear scope.

4. Rich Text Uses Triple-Quoted Fenced Bodies

Rich-text fields such as content accept either a same-line quoted string or a triple-quoted fenced body. Both forms produce the same Markdown-capable value and support placeholder interpolation. The quoted form is convenient for short content; the fenced form is preferred for multiline prose.

Example:

text
  handle: description
  content:
    """
    Markdown goes here.

    **Bold** and *italic* should work.
    """

This is currently preferred over a custom markdown-only fence because it is visually obvious and easy to validate.

The opening and closing """ fences are recognized only when they appear alone at the fenced body’s indentation level. The same three-character sequence inside an ordinary line of prose is literal content and needs no escape.

When parsing the body, the fence’s indentation is removed from every content line and any additional indentation is preserved for Markdown. A nonblank content line indented less than the fence is an error.

The newline after the opening fence and the newline before the closing fence are structural and are not part of the rendered value. Blank lines deliberately authored between those boundaries, including additional leading or trailing blank lines, are preserved.

V1 rich text intentionally supports only plain paragraphs, bold, italic, strikethrough, underline, unordered bullet lists, and tables. Raw HTML, links and automatic links, task checkboxes, headings, block quotes, code constructs, and other Markdown extensions are not rendered as formatting. Tables remain supported because they are common enough in Jump prose despite their heavier authoring cost.

Inline delimiters are **bold**, *italic*, ~~strikethrough~~, and ++underline++. The underline extension exists because Markdown has no standard underline delimiter and raw HTML is not allowed.

5. Repetition Is Usually Repeated Declarations

Repeated declarations are the default list form.

Examples:

tag: magic
tag: combat
group: perks

Comma-separated list fields are not supported in v1. Repetition is the only list form, giving the parser, formatter, and structured editor one canonical representation.

Core Grammar Mechanics

The following mechanical rules are settled for the first version of the language. Declaration-specific sections may narrow these rules where a field is intentionally repeatable or ordered.

Encoding and Line Endings

  • source files must be valid UTF-8; invalid byte sequences are errors and are not guessed as another encoding
  • a UTF-8 byte-order mark is accepted on input, but explicit formatting removes it
  • LF and CRLF line endings are accepted, and ordinary editing preserves the existing style
  • explicit formatting and distributable package export emit LF line endings

Whitespace and Comments

  • each indentation level is exactly two spaces
  • tabs used for indentation are a diagnostic error
  • a line whose first non-whitespace character is # is a comment
  • inline comments are not supported in v1; this keeps values such as color: #3366cc unambiguous
  • inside a triple-quoted fenced body, a line beginning with # is literal Markdown content rather than a comment

Scalar Literals

  • integer literals are base-ten values matching -?[0-9]+; leading +, digit separators, decimals, and exponent notation are not supported
  • leading zeroes and negative zero are accepted, but explicit formatting emits the canonical numeric value, so 007 becomes 7 and -0 becomes 0
  • boolean literals are exactly the lowercase bare tokens true and false; quoted equivalents are strings, and aliases or differently cased forms are invalid
  • v1 has no null literal; optional fields are unset by omission, and clearing one through structured editing removes it from source
  • one physical line may contain only one field; a second field-shaped token and unquoted colon in the first field’s value is a syntax error, while a colon inside a correctly quoted string remains ordinary text
  • a field with a colon but no same-line value introduces an indented value only when that field explicitly supports one, such as a fenced content body; it never implicitly means an empty string, which is written as ""

Field Order and Repetition

  • fields may be written in any order unless their declaration explicitly gives them ordered semantics
  • the formatter emits a canonical field order
  • duplicate non-repeatable fields are errors rather than implicit overrides
  • ordered repeated declarations, including conditional text variants and layout children, retain source order

Handles and References

  • top-level handles occupy separate namespaces by declaration kind
  • owned text, image, and input handles are scoped to their owner and declaration kind; the same handle may be reused across those kinds
  • choice-source handles are scoped to their section
  • layout container handles are scoped to their layout
  • forward references and references across package files are allowed
  • references are resolved and validated after all package files have been merged
  • user-facing section and choice names are not identity keys and may repeat without a diagnostic; interfaces disambiguate them with containing context or handles when necessary
  • choice group names occupy one package-wide membership namespace across every file and section
  • a section-local choice-source group selector resolves against that package-wide namespace
  • group names use the same canonical ^[a-z0-9]+(?:_[a-z0-9]+)*$ syntax as handles; tags remain unrelated free-text strings
  • resource names use that same canonical syntax so costs and grants cannot create visually ambiguous duplicate balances

Package Order

Where declaration order has observable meaning, the merged order is deterministic: declarations in jump.jdef come first, followed by choices.jdef, then layout.jdef; source order is retained within each file. Declaration-specific ordering rules still apply after that merge.

Errors, Recovery, and Formatting

  • unknown fields are errors and diagnostics should suggest a close known spelling when possible
  • the source editor may recover from only deterministic, low-risk errors whose repair does not require guessing author intent
  • when deterministic recovery is not possible, preview retains the last valid document while showing the current diagnostics
  • editing preserves the author's formatting; an explicit format action applies canonical indentation, field order, and spacing

The exact field compatibility matrix for each declaration kind remains to be specified.

Package Structure

Rigid Project Structure

The package structure should be fixed by the language/tooling rather than left to author-defined imports/includes.

This avoids turning file organization into a module system.

Distributable Container

A distributable Jump package uses the user-facing .jmp extension and is internally a standard ZIP archive. The application presents it as one Jump package; the ZIP implementation detail remains available to standard inspection tools without being exposed in ordinary workflows.

Canonical exports place jump.jdef, optional companion definition files, and assets/ directly at the archive root. Import also accepts the complete package beneath one enclosing directory, then treats that directory as the package root.

Archive validation rules:

  • only regular files are permitted; symbolic links, hard links, device entries, and other special archive entries are rejected
  • absolute paths, parent traversal with .., and any normalized path escaping the package root are rejected
  • paths that collide after separator normalization, Unicode normalization, or case folding are errors so a package has the same contents on case-sensitive and case-insensitive platforms
  • the archive root is limited to the known .jdef files and assets/; additional regular asset files may remain even when no current declaration references them
  • import applies implementation-defined limits to entry count, individual compressed and expanded size, total expanded size, compression ratio, image dimensions, and decoded image memory; exceeding a limit rejects the package with a clear safety diagnostic rather than partially importing it

Every file beneath assets/, referenced or not, must be a valid graphical asset in the initial allowlist: PNG, JPEG, GIF, WebP, or AVIF. Validation checks the filename extension against detected file signatures and requires the corresponding image decoder to validate the content. A mismatched extension, malformed image, unsupported format, non-graphical file, or file exceeding decode limits rejects the entire import with a prominent potentially unsafe-package diagnostic. SVG is not accepted in v1 because it may contain scripts, external references, and other active content. Import never exposes rejected asset bytes to a renderer and never keeps a partial package.

Current File Roles

jump.jdef

Required.

Responsibilities:

  • declare the jump root
  • define package identity and metadata
  • contain package-wide secondary resource declarations
  • act as the primary file in single-file mode
  • allow other top-level declaration kinds when the author chooses not to split them out

choices.jdef

Optional.

Responsibilities:

  • contain only top-level choice declarations

layout.jdef

Optional.

Responsibilities:

  • contain only top-level theme declarations
  • contain only top-level section-layout declarations
  • contain only top-level choice-layout declarations
  • contain only top-level trait-layout declarations

assets/

Optional.

Responsibilities:

  • hold referenced images and similar external files

Merge Rules

The loader should merge the package into one canonical jump document.

Current direction:

  • jump.jdef is always authoritative for jump/package identity
  • choices.jdef and layout.jdef are organizational companion files, not independent modules
  • there is no file-level import/include syntax

Mixed Placement Policy

The current agreed policy is intentionally soft for author ergonomics:

  • jump.jdef may contain everything in single-file mode
  • if choices.jdef exists, mixed placement remains valid but should produce a warning
  • if layout.jdef exists, mixed placement of presentation declarations remains valid but should produce a warning

Tooling should help the user normalize the package rather than merely complain.

The editor should eventually support guided extraction, such as:

  • moving top-level choice declarations into choices.jdef
  • moving theme, section-layout, choice-layout, and trait-layout declarations into layout.jdef

Top-Level Declarations

The agreed direction is to keep the grammar consistent across files.

Top-level declarations should use the same syntax everywhere. File type limits which declarations are allowed in that file, but declarations do not change shape depending on location.

Current Allowed Declaration Kinds

In jump.jdef

  • exactly one top-level jump
  • top-level resource
  • top-level section
  • top-level choice
  • top-level theme
  • top-level section-layout
  • top-level choice-layout
  • top-level trait-layout
  • other declaration kinds may be added later if needed

In choices.jdef

  • top-level choice only

In layout.jdef

  • top-level theme only
  • top-level section-layout only
  • top-level choice-layout only
  • top-level trait-layout only

Declaration Shape

Keyword-Only Start

Declarations should begin with a keyword only.

Identity should not be positional.

Preferred form:

choice
  handle: flight
  name: "Flight"

Not:

choice flight
  name: "Flight"

This keeps the language regular and simplifies parser and editor behavior.

Handles Are Author-Facing, Not Internal IDs

The author-facing reference token should be called handle, not id.

Internal IDs remain model-only.

Handle Requirements

For top-level referenceable declarations other than the unique root jump:

  • section and choice require both a stable handle and a user-facing name
  • every choice-source and owned text, image, and input block requires a stable handle
  • every top-level theme, section-layout, choice-layout, and trait-layout declaration requires a stable handle
  • if handle exists, name may be omitted where that makes sense
  • presentation declarations may rely on their required handle alone; a user-facing name is optional

Derived Handles

Tooling may generate required handles for author convenience, but generated handles are materialized into source and remain stable afterward.

Current direction:

  • when creating a declaration with a required handle, tooling may derive and immediately write an initial handle from its name or conventional role
  • derived handles should be normalized consistently
  • renaming a declaration does not automatically change a materialized handle

Current agreed handle syntax:

  • authored handles must match ^[a-z0-9]+(?:_[a-z0-9]+)*$
  • lowercase ASCII letters, digits, and single separating underscores are the only allowed characters
  • handles may begin with digits
  • uppercase letters, whitespace, hyphens, punctuation, repeated underscores, and leading or trailing underscores are invalid rather than silently normalized by the parser
  • the Editor may generate a canonical handle or offer a deterministic Quick Fix, but the corrected canonical value is written into source

Current generation examples:

  • "My Thing!" -> my_thing
  • "3 Perks" -> 3_perks

Handle Generation

Generated handles are conveniences for creating required source fields, not implicit identities.

Current collision rule:

  • collisions should not be silently resolved by automatic suffixing in saved source
  • collisions should instead produce diagnostics and prompt explicit author correction

Semantic vs Presentation Separation

Sections Reference Layouts; They Do Not Inline Layout

Sections should reference layouts by handle rather than containing their own inline layout trees.

This should be true in both single-file mode and split-file mode.

Example direction:

section
  handle: origins
  name: "Origins"
  layout: origin_section

with the presentation declared separately:

section-layout
  handle: origin_section

Choices Follow the Same Rule

Choices should not inline their presentation template.

They should reference a choice-layout by handle where needed, or inherit from section/jump/system defaults.

This keeps presentation concerns out of semantic declarations.

Layout Resolution

The parser/runtime should have built-in default layouts for sections and choices.

These built-ins apply when the author does not specify anything more specific.

If a section, choice, Jump default, or expansion override explicitly names a layout declaration that does not exist, the Editor reports a warning and previews with the applicable built-in default layout. The unresolved reference is an error in a distributable package. This differs from an absent typed content target inside an existing reusable layout, which is valid and simply collapses.

Section Layout Precedence

Current direction:

  1. section-specific layout reference
  2. jump-level default section layout
  3. built-in section layout

Choice Layout Precedence

Current direction:

  1. choice-specific layout reference
  2. choice-layout specified by the section expansion using that choice
  3. jump-level default choice layout
  4. built-in choice layout

The layout used by a section expansion should be presentation-only for that rendering context. It should not mutate the choice definition itself.

This means a choice-layout may be selected from several places:

  • directly on the choice
  • on the expand node inside the surrounding section-layout
  • from a jump-level default
  • from a built-in system default

The section expansion override is contextual presentation only. It does not rewrite the choice's own preferred layout.

Trait Layout Direction

Trait display should be author-controllable through a dedicated trait-layout declaration.

Current direction:

  • trait-layout is a top-level presentation declaration
  • it should not be fundamentally different from a choice-layout
  • it should use the same general layout-tree grammar
  • its initial built-in slot vocabulary should remain minimal

Current minimal slot direction:

  • name

Additional trait-owned text and image content should be placed through typed handled-content leaves, just as prose and visuals are handled in choice-layout.

Layout Node Vocabulary

Built-In Default Layouts

The renderer provides intentionally plain built-in section and choice layouts. Authors use them automatically when neither the declaration nor the Jump root selects an authored layout.

Built-in layouts render only their supported built-in slots and, for sections, declared choice sources and direct choice associations. They do not discover or automatically place arbitrary owned text, image, or input blocks. Those blocks render only when an authored layout references them explicitly, avoiding nonstandard discovery rules and unintentional hodgepodge presentation.

The selected default section presentation is a vertical stack with standard spacing: the section name slot appears first, followed by every choice source and direct choice association in declaration order. Each source receives a compact source wrapper containing its contextual roll slot and one expand; a direct choice renders once with its normal contextual/default choice layout.

The selected default choice presentation is a compact vertical stack. An inline header places name and cost apart, followed by tags, then an inline action row containing control and choice-level roll. This includes every built-in choice slot without discovering arbitrary owned blocks.

Built-in layout containers are implementation-owned and do not expose author-facing handles. Equivalent authored layouts use ordinary handled containers.

At runtime, empty or inapplicable slots reserve no space. A container whose children all collapse for that reason also collapses. The structured layout editor still shows those nodes as authoring placeholders so their positions remain understandable.

Authored layouts replace presentation only; they do not change semantic membership or state.

The current agreed direction for layout trees is:

  • exactly one root node per section-layout, choice-layout, or trait-layout
  • the root node must be a container: stack, inline, wrap, or grid
  • text, image, input, slot, rule, and expand are never valid as the layout root
  • container nodes:
    • stack
    • inline
    • wrap
    • grid
  • leaf/special nodes:
    • text
    • image
    • input
    • slot
    • rule
    • choice inside a section layout
    • expand

    A grid requires columns as an integer from 1 through 12. This is the authored maximum; responsive rendering may reduce the effective count for narrower space but never exceeds it.

    Each direct grid child occupies one cell in source order. V1 has no row-span or column-span fields; authors compose wider regions with nested containers or a different surrounding layout.

Node Shape

Container nodes are nested declaration blocks with author-defined handles.

Simple leaf references use a compact scalar form.

Typed text, image, and input references, as well as slot, support equivalent compact and block forms. Compact leaves use forms such as text: description, image: visual, input: quantity, or slot: cost. A block leaf requires target and may add presentation fields:

text
  target: description
  padding: sm

slot
  target: cost
  align: end

A horizontal separator is a standalone targetless leaf:

rule

rule renders a theme-aware horizontal line across its available layout width. It has no target, handle, child nodes, or v1 presentation fields; surrounding containers control its spacing. Other leaf nodes likewise do not have handles or children. A typed leaf’s block form does not create a different semantic node; it only provides room for presentation fields.

The same typed content target or slot target may appear more than once in one layout. Each occurrence is an independent presentation node over the same underlying content or control. The generic ref form is not supported because declaration-kind namespaces allow matching handles.

A typed content leaf whose target is not present on a particular section or choice is valid and collapses without reserving runtime space. This permits one authored layout to be reused across content with different optional fields. The Editor warns about an absent target by default and shows the leaf as a structured-authoring placeholder; users may suppress that diagnostic with editor.warnMissingLayoutTargets. A missing target does not make a distributable package invalid.

Current container-handle rules:

  • every stack, inline, wrap, and grid node must declare a handle
  • container handles must be unique within their owning section-layout, choice-layout, or trait-layout
  • container handles use the same normalization rules as other authored handles
  • container handles identify levels for authoring, navigation, diagnostics, and refactoring
  • the nested source structure remains authoritative for parent/child relationships; a handle identifies a container but does not define its parent
  • when a layout is created, tooling should give its root container the explicit handle root; authors may rename it
  • containers may temporarily have no children; this produces a warning, shows an authoring placeholder in the Editor, and contributes no runtime content

Example direction:

choice-layout
  handle: origin_card

  inline
    handle: card
    gap: md
    align: start

    image: visual

    stack
      handle: details
      gap: sm
      slot: name
      text: description
      slot: cost

    slot: control

section-layout
  handle: origin_section

  stack
    handle: root
    gap: md
    text: intro_text

    expand
      source: main
      using: origin_card

Expansion Scope

expand should remain intentionally narrow in v1.

Current direction:

  • expand is valid only inside section-layout in v1
  • expand is not valid inside choice-layout or trait-layout
  • expand targets a named section-local choice source
  • expand may specify using for a choice-layout override
  • expand should not query descriptive tags or groups directly
  • an expand naming a choice source absent from the rendered section produces an Editor warning and a distributable-package error; unlike optional typed content leaves, source expansion is structural and does not silently collapse in a valid package
  • one section layout may expand a given choice-source target at most once; duplicate expansion is an error because it would render the same interactive controls repeatedly
  • a section with no choice-source is a valid informational section and produces no source-related warning
  • a declared choice source that currently matches no choices produces a warning
  • when an explicit section layout omits a populated choice source, the source remains valid but produces an unreachable-source warning

Direct Choice Placement

A section may associate a named placement with one top-level choice when unrelated controls need to share a section without pretending to be a selectable group.

section
  handle: identity
  name: "Identity"
  layout: identity_section

  choice
    handle: gender_field
    target: starting_gender

  choice
    handle: age_field
    target: starting_age

The section block names both the owner-local placement and its top-level target. The layout places it through compact-only scalar leaves; this is not expansion and has no block form.

section-layout
  handle: identity_section

  grid
    handle: root
    columns: 2
    choice: gender_field
    choice: age_field
  • forward references to top-level choices are allowed
  • one section may associate a target once, and one layout may place each association once
  • unresolved targets or placements are distributable-package errors
  • an associated choice omitted from an explicit layout produces an unreachable-choice warning

Choice Sources

Sections need a semantic way to associate choices with themselves without making layouts decide membership.

Current direction:

  • a section may define one or more nested choice-source declarations
  • each choice-source has a required section-local handle
  • each choice-source accepts zero or one group selector
  • a source without a group is valid WIP structure but cannot contain choices and produces a warning
  • group is not repeatable on choice-source in v1; authors combine existing categories by adding one shared group to the relevant choices
  • a choice-source is where semantic membership/filtering is declared
  • expand source: ... resolves against those section-local handles

Current rules:

  • if a section has exactly one choice-source, expand may omit source, but the source declaration still requires its handle
  • if source is omitted when the rendered section has zero or multiple choice sources, the Editor warns and renders no expansion for that node during recovery; the ambiguity is a distributable-package error
  • the handle is the stable identity used by layout references and persisted source-level roll records
  • renaming, reordering, or adding other sources does not change an existing source handle
  • choice-source should own grouped pick behavior such as single vs multi rather than forcing those concepts onto each individual choice

Example direction:

section
  handle: origins
  name: "Origins"
  layout: origin_section

  choice-source
    handle: main
    group: origins
    mode: single

In this model:

  • the section decides which choices are associated with it
  • the section-layout decides where those associated choices render

Slot Vocabulary

The initial built-in slot vocabulary is intentionally small.

Current direction:

  • name
  • cost
  • control
  • roll
  • tags

Current scope:

  • name, cost, control, and tags are built-in choice-layout slots
  • roll is a built-in slot wherever the current render context exposes a roll control, including:
    • choice-layout for choice-level resolution
    • section/source rendering contexts for source-level resolution

Prose and visual content should not use dedicated built-in slots. They should be referenced through handled text, image, and input declarations via matching typed layout leaves.

Jump Direction

The top-level jump declaration is the place for root jump metadata and jump-wide defaults.

Every Jump has an implicit engine-owned primary resource with the stable handle jump_points. It defaults to the display name Choice Points and abbreviation CP. An ordinary Jump defaults to a starting balance of 1000, while a native Gauntlet defaults to 0. Authors never need to declare this resource, and supplements may rely on it existing.

Every secondary resource referenced by costs or grants requires an authored resource declaration. Its initial field is optional and defaults to zero. Undeclared secondary-resource references are distributable-package errors, while the Editor retains them as WIP diagnostics.

Structured editing resolves the exact parsed occurrence of every scalar, repeated, or conditional field. Clearing or replacing one occurrence never broadens across a newline into a neighboring field. Rich-text fence extents include both delimiters, so converting between a scalar and fenced value removes the prior representation atomically while preserving unrelated source byte-for-byte.

Secondary resources are top-level declarations in jump.jdef, alongside jump and section; they are not nested inside the root Jump declaration.

Current direction:

  • no handle
  • required integer format
  • name
  • optional package description
  • one or more repeated author fields
  • required version
  • optional boolean gauntlet
  • optional starting-points
  • optional points-name
  • optional points-abbreviation
  • optional default section-layout
  • optional default choice-layout
  • optional default trait-layout

Current rules:

  • jump is unique per package, so a handle adds no value here
  • format is required and selects the markup schema used to parse the package; the first schema uses format: 1
  • a package declaring a newer format than the application supports is rejected with a compatibility diagnostic that identifies the required newer application support
  • the parser does not attempt best-effort interpretation of an unknown format
  • supported older formats are deterministically migrated in memory to the current canonical model without rewriting installed package source
  • the Editor offers an explicit, reviewable format-upgrade action for older source projects; merely opening or previewing the project does not upgrade its files
  • logical package identity is the declared Jump name together with its repeated author values; identity collisions are visible metadata conflicts for the community and application to surface rather than being hidden behind generated identifiers
  • identity comparison applies Unicode normalization, trims leading and trailing whitespace, collapses internal whitespace, and compares case-insensitively while preserving authored text for display
  • versions with the same name and author identity remain distinguishable by their displayed version and application-computed exact-content hashes
  • at least one author is required and the field is repeatable rather than packed into a list
  • a work without an identified author uses an explicit user-facing value such as author: "Anonymous" rather than omitting the field
  • author order is preserved for display but does not affect logical package identity; identity compares the authors as an order-independent set
  • repeating the same author value within one Jump declaration is an error
  • version is required user-facing metadata so installed releases can be distinguished in the library and chain
  • description is concise package-level library and preview metadata; it is distinct from handled text blocks rendered inside sections and choices
  • version is user-facing metadata, not the system's authoritative internal compatibility key
  • gauntlet defaults to false; gauntlet: true declares that the installed package is intrinsically a Gauntlet
  • omitted starting-points defaults to 1000 for an ordinary Jump and 0 for a native Gauntlet; an explicit authored value overrides either default
  • points-name defaults to "Choice Points", and points-abbreviation defaults to "CP"
  • starting-points accepts any literal integer, including an authored negative starting balance, and does not accept symbolic cost tokens
  • the package declaration is immutable chain truth: a native Gauntlet cannot be converted into an ordinary Jump by chain state
  • an ordinary installed Jump may receive entry-scoped Gauntlet rules from an explicit user action or supplement; that applied status belongs to the chain entry rather than package markup and reduces the ordinary starting-point contribution to 0
  • native and applied Gauntlet sources are idempotent rather than cumulative; explicit drawback, quest, supplement, and other resource grants continue to add to the resulting balance
  • these fields change presentation or initial balance without changing the engine-owned jump_points handle
  • internal compatibility/version tracking should continue to rely on stronger internal mechanisms such as hashing rather than trusting authored version strings as machine truth

Example direction:

jump
  format: 1
  name: "Example Jump"
  description: "A concise premise shown while browsing this Jump."
  author: "Author One"
  author: "Author Two"
  version: "1.0"
  gauntlet: false
  starting-points: 1000
  points-name: "Choice Points"
  points-abbreviation: "CP"
  section-layout: default_section
  choice-layout: default_choice
  trait-layout: default_trait

A native Gauntlet uses the same Format 1 root declaration:

jump
  format: 1
  name: "The Arena"
  author: "Example Author"
  version: "1.0"
  gauntlet: true

Because starting-points is omitted, this package contributes 0 jump_points before explicit grants. This is distinct from an ordinary Jump that a user or supplement treats as a Gauntlet for one chain entry; applied status is never written back into package source.

Resource Direction

Secondary currencies are top-level package-wide declarations in jump.jdef. Their current field direction is:

  • required canonical handle
  • required name
  • optional abbreviation
  • optional initial, defaulting to 0

The handle is the stable identity used by costs, grants, balances, conditions, and summaries. It occupies the package-wide resource namespace and may not use the reserved engine handle jump_points.

The required name supplies expanded balance, tooltip, diagnostic, and accessibility text.

When abbreviation is omitted, compact interfaces use the full name or a visibly truncated form whose complete name remains available on hover and focus.

initial accepts a literal integer only, including negative values for authored debt or deficit mechanics. Symbolic cost-scale tokens are not valid starting balances. This authored starting state is not blocked by the user setting that governs optional overspending.

resource
  handle: warehouse_points
  name: "Warehouse Points"
  abbreviation: "WP"
  initial: 150

Section Direction

Sections should stay semantically lean.

Current direction:

  • required handle
  • required name
  • layout?
  • repeated nested choice-source
  • repeated nested direct choice associations
  • nested text
  • nested image

Current rules:

  • handle is the section’s stable package-local identity for navigation, owned choice sources, and layout references
  • renaming a section does not automatically change its handle
  • name is required semantic navigation and accessibility text even when the selected section layout does not visibly render a heading
  • a valid distributable package contains at least one top-level section
  • zero choices are valid, allowing an informational package, but a zero-section project remains an incomplete Editor draft and cannot be exported as a valid package
  • sections do not inline layout trees
  • a nested section choice block associates a placement with a top-level choice; it does not redeclare or inline that choice
  • source order defines section order in v1
  • section prose should be expressed through nested text blocks rather than special prose fields
  • sections do not currently need their own tags

Example direction:

section

  name: "Origins"
  layout: origin_section

  choice-source
    handle: main
    group: origins

Ownership of Content Blocks

Content should stay local by default.

Current direction:

  • section owns its text and image blocks
  • choice owns its content fields and subordinate content blocks
  • layouts reference handled owned content with typed text, image, or input leaves
  • layouts use slot only for the small built-in slot vocabulary such as name, cost, control, roll, and tags
  • only genuinely reusable/global declarations belong at the top level

This avoids turning the language into a global registry of every content node.

Section-Owned Blocks

Because layouts need to reference section-owned blocks, those blocks need author-facing handles.

Current direction:

  • every owned text, image, and input block requires a stable owner-local handle
  • tooling may generate conventional initial handles such as description or visual, but writes them into source
  • renaming or rearranging surrounding content does not change the block handle

Auxiliary prose should be represented as generic text blocks rather than as special one-off text fields or role-tagged variants.

text Direction

The current direction for text is intentionally lean:

  • required handle
  • optional content:
  • zero or more content when ...:

A text block may contain only conditional variants and renders nothing when none match. A block with neither base content nor conditional variants is allowed as WIP structure and produces a warning.

Example direction:

text
  handle: description
  content:
    """
    Base text.
    """

  content when rank = 2:
    """
    Alternate text.
    """

This replaces the earlier idea of special prose fields inside sections, choices, and grants. Rendered content prose should be authored uniformly as text blocks, with default renderers looking for documented conventional handles such as description where that is useful. The root Jump’s concise description remains package metadata for library cards and package headers rather than rendered section content.

Placeholder Direction

Placeholder interpolation should be supported in renderable string content using property handles such as {{companion_name}}.

Current direction:

  • placeholders are allowed in user-facing/renderable string values
  • placeholders are allowed in text.content
  • placeholders are allowed in quoted scalar strings such as name and alt
  • placeholders are not allowed in structural/reference fields
  • a placeholder naming no property defined by package grants produces an Editor warning and a distributable-package error
  • a known property that is currently unset for the active actor renders as an empty string without a diagnostic
  • if a name contains placeholders, it must not be used for implicit handle derivation

This keeps runtime interpolation out of parse-time structural identity.

image Direction

The current direction for image is also intentionally lean:

  • required handle
  • optional WIP src
  • optional alt

Example direction:

image
  handle: banner
  src: "origins.png"
  alt: "A banner for the origins section"

Current rules:

  • an image may temporarily omit src; it produces a warning and renders a compact authoring placeholder identified by its handle
  • an image without src is incomplete for package export even though the Editor can preserve and preview the WIP block
  • src is local/project-relative only in v1
  • remote image URLs are not part of the format
  • asset paths use portable forward slashes and must resolve inside the package directory
  • absolute paths, URI schemes, parent traversal with .., and any normalized path that escapes the package are errors
  • a safe path whose referenced file is missing produces an Editor warning and a missing-image placeholder during authoring
  • a missing referenced asset is an error when exporting or importing a distributable package
  • omitted alt renders as empty alternative text and produces an accessibility warning by default
  • users may suppress the missing-alt warning through editor.warnMissingImageAlt; suppression changes diagnostics only and does not modify package source
  • alt is a renderable text field and may therefore use placeholders and conditional when variants just like other renderable text fields
  • image sizing belongs in layout/presentation, not in the semantic image declaration

This same generic image block model should apply to choice-owned visual content as well. The difference is ownership context, not syntax. In practice, default choice layouts may look for an image block with a conventional handle such as visual.

input Direction

Inputs should be minimal structural declarations owned by a choice.

Current direction:

  • required handle
  • required selection
  • optional min and max where the selection kind supports a bounded count

Current supported selection values:

  • text
  • integer
  • select
  • companions

Inputs have no default selection kind because text, integer, select, and companion roster controls have different state and validation requirements.

Example direction:

input
  handle: companion_name_input
  selection: text

  grant
    kind: property
    handle: companion_name

Inputs do not need a name field. If the rendered UI needs visible labeling, that labeling should come from nearby authored content, typically text blocks, rather than from a special input-only label field.

When the owning choice becomes unselected, nested input values remain stored as dormant chain-entry state so reselection restores them. Dormant inputs do not apply grants, properties, costs, or other effects. Removing the chain entry deletes them with the rest of that entry’s state.

selection: companions is a runtime roster picker rather than an authored string list:

  • its values are stable companion record identities, not names or authored options
  • the available roster contains companions that exist at the current chain-entry evaluation point
  • max is required and must be a positive integer
  • min defaults to 0 and must not exceed max
  • the input prevents selecting the same companion more than once
  • authors label and explain the picker with nearby owned text, as with other inputs

Choice Direction

Choices should be structured around:

  • identity and organization
  • owned content
  • mechanics

Current direction:

  • required handle
  • name
  • layout?
  • repeated tag
  • zero or more repeated group fields
  • nested text
  • nested image
  • nested input
  • optional selection
  • optional continuity for a standardized Gender select
  • repeated nested mechanics declarations such as cost and grant

Current rules:

  • handle is the stable package-local identity used by saved selections, costs, grants, roll results, and references
  • the Editor may generate the initial handle from the choice name, but renaming the displayed choice does not automatically change its handle
  • name should remain required on choice
  • a choice may declare no groups; it remains valid and available in Editor navigation but is unreachable by v1 section choice sources
  • an ungrouped choice produces a warning rather than a package-validity error
  • a choice may belong to multiple distinct groups, but repeating the same canonical group on one choice is an error because membership is set-like
  • layout remains optional because section expansion usually supplies layout context
  • selection should default to toggle when omitted
  • current preferred selection values are:
    • toggle
    • text
    • integer
    • select
  • integer may carry min and max
  • text, integer, and select choices have an explicit unset state distinct from every valid value
  • a non-toggle choice applies its costs and grants only while it has a value
  • empty or whitespace-only text is unset; integer zero remains a valid value when allowed by the bounds
  • every non-toggle choice control must let the user return to unset, which removes its costs and grants during recalculation
  • manual integer selections may omit either or both bounds
  • an integer choice using resolution: random or resolution: either requires finite min and max values
  • min and max are inclusive
  • integer random resolution samples uniformly from every integer in the inclusive range
  • v1 has no integer step field; integer controls advance by one, and sparse numeric domains use selection: select
  • resolution is optional and applies only where the choice's own selection domain can be randomly resolved
  • current preferred resolution values are:
    • random
    • either
  • prose should be authored as nested text blocks with conventional handles such as description
  • choice-owned visual content should be authored as nested image blocks with conventional handles such as visual

Identity Properties

Origin, Species, Location, Gender, and Age communicate with the Chain Tracker through ordinary property grants. One Origin may write both background and species without coupling Location to either value.

choice
  handle: moon_elf
  name: "Moon Elf"
  group: origins

  grant
    kind: property
    handle: origin
    value: "Moon Elf"

  grant
    kind: property
    handle: species
    value: "Elf"

origin, species, location, and gender are strings; age is an integer. Origin, Species, and Location accept quoted literals or compatible string controls. Copied Gender requires selection: select, while copied Age requires selection: integer. Origin and Location never inherit. Age begins with the actor’s previous effective Age until an authored integer choice overrides it; clearing that control restores the derived value. Species resolves from an explicit current-entry property, then an enabled Classic Body Mod Bestial value such as Wolf Demi-Human, then Human.

Gender Continuity

continuity is valid only on a select choice that directly copies its control into exactly one gender property grant.

  • continuity: previous references the actor's preceding effective gender
  • continuity: original references Earth for the Jumper or acquisition identity for a companion
  • a referenced option present in the dropdown is the derived free default; other options retain authored costs
  • when the referenced value is unset or absent, the control begins unset and every option is free
  • explicit selections remain stable after upstream changes; clearing restores derived behavior

Choice Defaults and Inheritance

The current agreed defaults are:

  • omitted selection means toggle
  • omitted layout means the choice uses contextual or default layout
  • omitted resolution means manual-only entry/selection

Choice Resolution Direction

Rolling is not a separate selection kind. It is one way a selection is resolved.

Current direction:

  • choice-level resolution applies to choice-level value domains such as:
    • integer
    • select
  • current preferred authored values are:
    • random
    • either
  • omitted resolution means manual-only
  • if resolution: random, the value must be rolled and cannot be manually set
  • if resolution: either, the user may roll for a free value or manually choose and incur normal cost rules
  • for flat-cost integer and select choices, the exact recorded rolled value is free; another current value uses normal cost, and returning to the recorded value restores free resolution
  • for an integer choice with cost mode: each, the rolled integer is a free-rank allowance: selecting that many or fewer ranks is free, while selecting more charges only for ranks above the allowance
  • a random-only integer may be cleared to its normal unset state without erasing or hiding the stored roll; when rerolls are disabled, the visible result remains beside Claim, which restores that stored result without generating another roll
  • if a choice supports rolling, slot: roll should be available to position the roll control separately from the normal control

Example direction:

choice
  handle: age
  name: "Age"
  selection: integer
  min: 18
  max: 45
  resolution: either

  cost
    amount: small
    mode: flat

  grant
    kind: property
    handle: age

Choice-Source Mode And Resolution

Grouped pick behavior should live on choice-source, not on each individual choice.

Current direction:

  • choice-source may declare:
    • mode: single
    • mode: multi
  • omitted mode defaults to multi
  • choice-source may also declare resolution where the group itself is what is being randomly resolved
  • source-level rolling applies to both mode: single and mode: multi
  • a roll on mode: multi selects exactly one currently available child choice; already-selected children remain eligible
  • the rolled child is free while it remains the recorded roll result; if it was already manually selected, that existing selection becomes the rolled selection and its ordinary cost is removed during recalculation rather than toggling it off or creating a duplicate
  • the recorded child may be unselected without erasing its roll record; selecting it again restores its free cost
  • multi sources do not allow duplicate selections, so the roll pool contains each eligible child at most once; a reroll also excludes the current recorded roll result so replacement produces a different result
  • rerolling replaces the prior rolled result rather than adding another rolled selection; the previous result becomes unselected unless it is independently required by another state rule
  • each chain entry records whether each source-level roll has occurred and which child it produced
  • without the user setting chain.allowRerolls, a recorded roll cannot be rolled again; Editor preview rolls are nonpersistent sandbox state
  • removing a chain entry deletes its choices and roll records, so adding the package again creates a fresh entry whose rolls have not occurred
  • if source-level rolling is present, slot: roll in the relevant rendered context should position the group roll control rather than forcing a roll button onto each child choice

Choice controls, cost badges, roll affordances, and result communication for every supported combination are catalogued separately in Controls.

The current agreed grant direction is:

  • common grants such as grant: perk or grant: item should inherit from the choice by default
  • inherited values should include the choice name, conventional descriptive text blocks such as description, and tag values unless explicitly overridden later

Cost Direction

Costs should support both a common shorthand and an explicit multi-resource block form.

Current direction:

  • cost: 100 means a cost against the jump's primary currency
  • cost: small-style shorthand should also be valid using the symbolic cost scale
  • costs against different resources are cumulative
  • a choice may declare at most one cost for each resource
  • two shorthand costs are an error because both apply to the primary currency
  • a shorthand cost and an explicit block naming the primary currency are also a duplicate-resource error
  • the explicit block form is used for non-primary or otherwise more detailed costs
  • alternative-payment groups are not part of the v1 cost syntax; multiple valid cost declarations all apply

Example direction:

cost: 100

cost
  resource: supplement_points
  amount: 50

Both costs in this example apply. Repeating a cost for the same resource is an error and should be consolidated by the author:

# Invalid: both declarations cost primary currency.
cost: 100
cost: 100

# Valid equivalent.
cost: 200

Current rules:

  • shorthand cost applies only to the primary jump currency
  • block-form cost requires an explicit resource; omitting it is an error rather than another way to address primary currency
  • block-form cost requires amount; an incomplete cost block is an error rather than useful WIP structure
  • block-form amount accepts the same numeric, zero, cost-token, and add_* token forms as primary-currency shorthand
  • cost blocks accept mode: flat or mode: each; omitted mode defaults to flat
  • flat applies the resolved amount once whenever the choice is selected
  • each is valid only on an integer choice and multiplies the resolved amount by the selected integer value
  • an integer choice using mode: each requires an explicit min of zero or greater; negative quantities are invalid because they would reverse cost meaning
  • a positive amount spends the resource and a negative amount awards its absolute value while the choice is selected
  • cost: -100 is the concise drawback form for awarding 100 units of primary currency
  • omitted cost and cost: 0 both mean free; explicit zero is valid even though omission is shorter
  • negative symbolic syntax such as -small is invalid; symbolic awards use the explicit inverse token family such as add_small
  • cost accumulation is across distinct resources, not repeated declarations for the same resource

Grant Direction

Grant shorthand should exist only where the granted thing is usually the same thing the choice is visibly about.

Current shorthand direction:

  • grant: perk
  • grant: item
  • grant: companion

These shorthand forms inherit by default from the choice unless explicitly overridden later.

Current inherited values include:

  • choice.name
  • conventional descriptive text such as description
  • conventional visual image such as visual where relevant
  • choice.tag

Common shorthand grants may coexist with other grant declarations on the same choice.

Block-Form Grants

Block-form grants are required for kinds that are not naturally represented by the choice's own visible identity.

Every block-form grant requires an explicit kind. A block without one is an error rather than useful WIP structure.

Most visible grant declarations do not have author-facing handles. Forms and companions are the exceptions because arbitrary grants may reference their ownership targets. kind: form, block-form kind: companion, and kind: companion-import require stable package-local handles. Scalar grant: companion uses its owning choice handle. The application tracks visible-grant provenance through the exact installed-package hash, owning choice or input handle, immutable grant position, and any runtime record ID created after acquisition.

A kind: resource grant requires both a canonical resource reference and an amount. Omitting either is an error.

Resource-grant amount accepts any literal integer, including zero and negative values, or one of the base symbolic magnitudes trivial, small, medium, large, major, and extreme. Positive and symbolic values add to the resource; negative integers remove from it. The add_* token family is not valid here because the grant context already communicates addition.

Current required block-form kinds:

  • resource
  • trait
  • property
  • companion
  • companion-import
  • form

Example directions:

grant
  kind: resource
  resource: jump_points
  amount: 100

grant
  kind: trait
  name: "Dragon Form"
  layout: dragon_trait

grant
  kind: property
  handle: gender
  value: "female"

grant
  kind: companion
  handle: ember_fox
  name: "Ember Fox"

input
  handle: imported_companions
  selection: companions
  max: 2

  grant
    kind: companion-import
    handle: imported_companions

  grant
    kind: resource
    resource: jump_points
    amount: 600
    companion: imported_companions

Companion Grant Direction

grant: companion is the common shorthand for a choice visibly about acquiring one companion. It inherits the choice name, conventional description and visual content, and tags in the same manner as perk and item shorthand grants.

The block form kind: companion creates the same durable companion record while allowing inherited fields to be overridden. It requires a package-local handle; scalar companion shorthand uses the owning choice handle. The engine assigns the record a stable runtime identity, while the authored handle provides the package-wide target for companion-owned perks and currency. The authored name is display content and is never used as an identity key. Removing or deactivating the originating grant produces dependency review for later imports and owned records rather than silently retargeting them.

Companion Import Direction

kind: companion-import is valid only as a grant nested directly in an input whose selection is companions. Its required handle represents the selected runtime companions as one author-facing grant target. A positive resource grant must target that handle before any selected companion receives participation state for the current chain entry.

Current rules:

  • importing does not create a new chain companion; it records that an existing companion participates in this Jump run
  • the participation state records the current chain-entry ID in that companion's import history
  • the import is active only while both the owning choice/input and selected companion identity remain active
  • the import alone does not make a companion available in the Chain Tracker actor selector; at least one positive kind: resource grant must target the import handle
  • every selected companion receives the full authored amount of each targeted resource grant in a separate actor-owned balance; the amount is not divided among them
  • while rendering as an imported companion, ordinary costs, rolls, properties, perks, items, and other grants belong to that companion's state for this entry
  • the same companion may have only one active companion-import grant in a chain entry; a duplicate import is an error rather than a second allowance
  • companion: <handle> on a perk grant assigns that perk to every runtime companion represented by the purchase or import handle without itself authorizing choices
  • removing a selected companion after they have made choices requires impact review and removes that companion's entry-scoped selections and grants if confirmed

Trait Direction

Traits are user-visible catchall grants for things that are not standard perks or items.

Current direction:

  • trait should remain user-visible
  • a trait grant inherits the owning choice’s name, conventional description and visual content, and tags by default
  • explicit trait-grant fields override only the inherited fields they provide
  • trait may carry owned text and image content just like other visible grant-like content
  • a trait grant may specify an optional layout
  • when omitted, trait display should fall back to the jump default trait-layout or a built-in trait layout if one exists
  • the app may later support trait-specific collected-grant layouts so authors can control how traits are displayed distinctly from standard perks/items

Property Direction

Properties are engine values granted by authored content for the current chain entry.

Current direction:

  • every kind: property grant requires a canonical handle naming the destination property
  • property values may come from:
    • a literal value
    • the primary control of a choice
    • the associated control of a nested input
  • when value is present, it writes that authored constant instead of copying the owning choice or input control
  • when value is omitted, the property grant copies its owning control value
  • literal value supports quoted strings, integers, and the bare booleans true and false
  • there is no literal null value; when the owning choice becomes inactive, its property grant is removed and the property may return to unset
  • property grants do not carry into later chain entries; the engine separately seeds Gender and Age identity continuity
  • properties are readable in when conditions and placeholders
  • multiple active grants may write one property only when they resolve to the same typed value; this produces an informational diagnostic
  • differing active values for one property are an ambiguity error; property evaluation never uses source order or last-write-wins behavior
  • properties do not use the shorthand inheritance model meant for perks/items
  • reserved engine-critical properties use documented standardized types and control requirements

Ordinary authored properties do not require separate top-level declarations in markup. They come into existence through the grants that write them.

Selection Option Direction

Selections such as select should support repeated quoted options:

option: "Male"
option: "Female"
option: "Other"

Current direction:

  • options are renderable quoted strings
  • the quoted option text is also its selected and persisted value; options do not require handles, separate values, or block declarations
  • one select domain may not repeat an identical option string; an exact duplicate is an error because it almost certainly indicates an authoring mistake
  • a select domain may contain zero options as valid WIP structure; it produces a warning, renders as a disabled empty control, and cannot be randomly resolved until at least one option is available
  • options may use when variants just like other renderable text
  • select-like properties resolve to strings
  • when comparisons against those properties use quoted strings
  • changing option text creates a changed value in that package version; immutable packages already present in chains retain their original option text and state
  • if the currently selected value is no longer present in the resolved option set, that should produce a diagnostic rather than silently remapping or erasing the selection

Current reserved engine property set:

  • origin
  • species
  • location
  • gender
  • age

Grant Override Semantics

When block-form grants override only part of the inherited common case, the override should be additive rather than all-or-nothing.

Current direction:

  • explicitly provided fields override inherited ones
  • omitted fields may still inherit where inheritance is meaningful

Tag System Direction

Tags are free-text, author-defined semantic metadata and the primary search vocabulary for perks, items, companions, and other content accrued by a chain. Detailed identity, relationship, search, badge, color, and user-override behavior is maintained in the separate Tag System Design.

Markup tags are deliberately only strings:

choice
  name: "Reality Warping"
  tag: magic

  grant
    kind: perk
    tag: "Reality Alteration"

Current rules:

  • choice continues to accept repeated tag fields
  • block-form grant declarations may add tags to the granted record
  • common grants inherit choice tags under the existing inheritance rules
  • tag inheritance is strictly additive; grant tags cannot replace or remove choice tags, and there is no tag-removal field
  • text, image, layout, and theme declarations are not taggable
  • sections remain untagged in v1 unless a concrete navigation need appears
  • bare and quoted forms are both string values; quoting allows whitespace and punctuation
  • runtime tag identity applies Unicode compatibility normalization and case folding, converts every run of whitespace, underscores, and Unicode dash punctuation to one ASCII space, and trims the result
  • a tag whose canonical identity is empty is an error, as is repeating the same canonical identity on one owner
  • badges do not preserve cosmetic source spelling; each canonical word is displayed with its first letter capitalized except for the lowercase particles a, an, and, as, at, but, by, for, from, in, nor, of, on, or, per, the, to, via, and vs; particle position does not change this rule
  • there are no tag declarations, handles, author relationships, or author badge styles

The application uses the canonical identity for display, searching, relationships, and styling while leaving imported source text unchanged. For example, lord_of_the-great_rings displays as Lord of the Great Rings. Parent/child and alias rules are user-owned settings. Badge styling, animation, and color families use built-in defaults or user settings. None of them change the Jump document.

Field Placement

Presentation fields should live in presentation/layout declarations rather than in semantic content declarations.

    • stack
    • inline
    • wrap

    • text

Diagnostic Policy

Layout-field compatibility uses these levels:

  • an unknown presentation field is an error
  • a known field on a node type that does not support it, such as columns on stack, is an error
  • a supported field with no practical effect for the referenced content, such as text-color on an image leaf, produces a warning rather than a parse failure
  • mutually exclusive supported fields, such as size together with width or height, are an error

Information diagnostics explain meaningful valid behavior when no author action is required. They should be contextual and sparse rather than emitted for every ordinary default. Useful examples include noting identical active property writers, explaining why an inapplicable slot collapsed when its node is inspected, and showing the canonical identity or generated label of a normalized tag on demand.

Theming

Theming should be supported early rather than deferred.

Current direction:

  • the system provides a built-in set of color tokens
  • jumps may define additional theme tokens
  • built-in tokens and jump-defined theme tokens are part of the same effective color-token space
  • color-accepting fields may use either:
    • a color token
    • a six-digit #RRGGBB hex color value
  • three-digit shorthand and alpha-bearing hex forms are invalid in v1
  • hexadecimal digits are case-insensitive; the formatter emits uppercase digits

Current conflict rule:

  • built-in color token names are reserved
  • theme declarations must not redefine built-in color token names
  • a theme token name conflict with a built-in color token should be a diagnostic error rather than a silent override

The exact declaration shape for theme definitions is now settled at a high level: themes exist to reduce repetition and provide a generic path forward beyond hardcoded color names.

Theme Declaration Direction

The current declaration direction for themes is:

  • use a top-level theme declaration
  • allow theme in jump.jdef
  • allow theme in layout.jdef
  • use the same mixed-placement warning model as other split-file declarations
  • define one token per declaration rather than a large map/blob structure
  • require exactly one color per theme declaration; missing or repeated color fields are errors

Example direction:

theme
  handle: primary
  color: #3366cc

theme
  handle: accent
  color: #ff9900

This means the effective color-token space is a union of:

  • reserved built-in color names
  • user-defined non-conflicting theme token names

Conditional Renderable Text

Rank- or count-dependent renderable text is a real authoring need.

The current agreed direction is:

  • support conditional variants on renderable text fields
  • current renderable text fields include:
    • content
    • name
    • alt
  • do not introduce a general conditional-field pattern beyond renderable text fields in v1

This keeps conditional prose readable and keeps validation narrower and easier to explain.

Condition Scope for Renderable Text Variants

The condition language for renderable text when variants should remain intentionally narrow and readable in v1.

Current preferred examples:

  • rank = 1
  • rank >= 2
  • count = 3
  • count >= 4
  • gender = "female"
  • gauntlet
  • companion_name
  • !companion_name

Arbitrary rule expressions are not currently desired in this syntax.

V1 condition expressions support property truthiness, ! falsiness, equality and inequality, numeric comparisons, and, or, and parentheses. Function calls and arithmetic are not supported.

Precedence is parentheses, then !, then comparisons, then and, then or. Negation may apply to a property or a parenthesized expression.

Bare-property truthiness treats unset as false, uses a boolean’s value, treats integer zero as false and other integers as true, and treats empty strings as false and nonempty strings as true.

Comparisons do not coerce types. Strings compare with quoted strings, integers with integers, and booleans with bare true or false. Ordering operators accept integers only. A statically provable type mismatch is an authoring error.

At runtime, conditions and placeholders read the currently viewed actor’s property state in the selected chain entry. Ordinary earlier properties are not retained. Engine-provided Gender and Age identity seeds and effects from the current entry’s choices are available, but properties acquired later never are. Companion view evaluates against that companion rather than silently reading the Jumper’s state.

gauntlet is a reserved read-only engine boolean, not an authored property destination. Editor preview derives it from the package’s native declaration; Chain Tracker evaluation also includes active entry-scoped user and supplement sources. This lets authored presentation react consistently without exposing a grant that could counterfeit package or chain status.

A condition referencing a property that no package grant defines produces a WIP warning in the Editor and is an error when exporting or importing a distributable package. Reserved engine values such as gauntlet are exempt because their types and provenance are defined by the format contract.

Variant Matching Order

when variants are evaluated from top to bottom. The first matching variant wins, and evaluation stops. Base renderable text is used only when no variant matches.

Variant source order is therefore meaningful and must be preserved by the formatter. More specific conditions normally belong before broader conditions.

content when rank >= 4:
  """
  Mastered description.
  """

content when rank >= 2:
  """
  Improved description.
  """

A broad earlier condition can make a later condition unreachable. For example, placing rank >= 2 before rank >= 4 means the latter can never be selected. The validator should warn when it can statically prove this kind of shadowing and should identify the earlier variant responsible.

Companion Participation

Companion acquisition and per-Jump participation are distinct mechanics:

  • grant: companion or kind: companion creates a durable companion record in the chain
  • selection: companions selects existing companion records by stable runtime identity
  • a nested kind: companion-import grant identifies those selected companions under a stable package handle
  • a positive resource grant targeting that handle authorizes the selected companions for the current chain entry and initializes a separate resource balance for each

Complete example:

choice
  handle: import_companions
  name: "Companion Import"
  selection: toggle
  cost: 200

  text
    handle: description
    content:
      """
      Import up to two existing companions. Each receives 600 points.
      """

  input
    handle: imported_companions
    selection: companions
    min: 1
    max: 2

    grant
      kind: companion-import
      handle: imported_companions

    grant
      kind: resource
      resource: jump_points
      amount: 600
      companion: imported_companions

A kind: companion-import grant does not carry resource or amount. Currency uses the ordinary resource-grant fields plus companion: <import-handle>, so imported and purchased companions share one targeting mechanism. At least one such grant must resolve to a positive amount for the import to authorize participation.

kind: companion-import is valid only as a nested grant of an input with selection: companions. Other placements are errors because they provide no selected roster to target.

The Chain Tracker evaluates this in order: the Jumper buys the choice, the input offers eligible stable companion records, and the targeted resource grant gives each selected identity an entry-scoped actor state with 600 jump_points. Only then does that companion appear in the current Jump's actor selector. Names remain presentation and may change without breaking the import reference.

Amended Format 1 Grants

This section records the quantity, rank, and form additions incorporated into Format 1 before release. They amend Format 1 in place and are not a Format 2 proposal. The schema, parser, validator, conformance fixtures, runtime model, and documentation implement them together.

Explicit Quantity Semantics

Format 1 provides explicit quantity metadata for durable visible grants. Quantity and rank are different measures and must not be inferred from one another:

MeasureMeaningExamplePresentation
RankThe acquired progression level, tier, or strength of one perk, item, or trait.Random Training acquired at rank 3.Rank 3 on a summary and Rank: 3 in details.
QuantityThe number of interchangeable copies or units acquired; it does not imply that any copy is stronger.Three identical healing potions.x3 on a summary and Quantity: 3 in details.

The discriminator is an optional measure: rank or measure: quantity field. A visible grant driven by an integer choice or input defaults to rank when the field is omitted. Authors write measure: quantity only when that integer represents interchangeable copies rather than progression. A non-integer choice produces an ordinary single acquisition and does not gain a rank badge merely because rank is the numeric default.

Default-rank shorthand example:

choice
  handle: random_training
  name: "Random Training"
  selection: integer
  min: 0
  max: 3

  cost
    amount: 100
    mode: each

  grant: perk

Block-form quantity example:

choice
  handle: healing_potions
  name: "Healing Potions"
  selection: integer
  min: 0
  max: 10

  grant
    kind: item
    measure: quantity

The amendment must preserve these semantics:

  • measure accepts exactly rank or quantity; omission means rank only when the grant copies an owning integer choice or input
  • on a block-form perk, item, or trait grant, measure applies to that grant
  • directly on a choice, the field applies to that choice’s single shorthand visible grant; it is invalid without exactly one grant: perk or grant: item shorthand
  • measure is valid only when the owning choice or input has an integer control; fixed literal quantities are outside this amendment
  • cost mode: each continues to describe cost multiplication and does not, by itself, declare quantity semantics
  • a resolved value of zero creates no acquired record for either measure; negative and non-integer measure values are invalid
  • authored measure is singular, so one acquisition cannot declare itself as both ranked and quantified
  • conditional descriptions and placeholders continue to read the authored choice/property context; adding quantity metadata must not replace or rename those values implicitly
  • the selected measure and value must persist with provenance and appear consistently in Inventory, companion profiles, Forms, and every shared perk/item/trait detail surface

Duplicate Acquisition Aggregation

Quantity also represents repeated acquisition of a similar record, including acquisitions produced by different choices, different Jump packages, or repeated instances of one exact package. Aggregation is a Chain Tracker projection and does not erase the individual provenance-bearing grant records.

  • each unquantified or ranked acquisition contributes one copy; an authored measure: quantity acquisition contributes its resolved quantity
  • the default-on chain.aggregateSimilarInventory projection aggregates records only when they have the same owner, perk/item kind, resolved name, and rank; unranked records match only other unranked records
  • perks never aggregate with items, different owners or forms remain isolated, and package identity, source Jump, and effective grant handle do not restrict similarity
  • the aggregate tag set is the stable union of every constituent record's tags
  • when similar aggregation is disabled, strict aggregation requires the same owner, kind, effective grant handle, exact installed-package source, resolved name, and rank; shorthand and block grants retain their existing effective-handle provenance
  • different ranks remain separate entries; two rank-3 acquisitions aggregate together, but rank 2 and rank 3 never do
  • an aggregate quantity greater than one displays an xN badge; quantity one remains visually implicit
  • a ranked aggregate may therefore show both its ordinary rank badge and an xN badge, but only when multiple copies with that same rank aggregate
  • an authored quantity record displays only xN, not a rank badge
  • aggregate details retain every contributing source and resolved description rather than discarding or deduplicating them; four or more rows use a bounded scroll region
  • removing or changing one contributing acquisition recomputes the aggregate and decreases, splits, or removes its quantity without mutating the remaining records

Form Grants and Form-Owned Perks

Format 1 also provides a durable form grant. A form is an accrued alternate body with its own profile and stable runtime identity. It is not an item, a temporary property value, or a mutually exclusive active state.

A form grant does not contain or automatically grant its perks. Any perk grant in the package may instead name the form that owns it, regardless of which section or choice contains either grant. The author selects that ownership relationship; the user does not select a recipient form.

Form grant:

choice
  handle: dragon_form
  name: "Dragon Form"
  cost: 400

  grant
    kind: form
    handle: dragon_form
    tag: transformation

    text
      handle: description
      content: "A scaled alternate body with wings and elemental resilience."

A perk in another section or choice may target that form with a single form field:

choice
  handle: reinforced_hide
  name: "Reinforced Hide"
  cost: 100

  grant
    kind: perk
    form: dragon_form

    text
      handle: description
      content: "Dragon Form gains armor without changing your other bodies."

When the choice uses ordinary perk shorthand, the form target is also available without expanding the grant into a block:

choice
  handle: draconic_resilience
  name: "Draconic Resilience"
  cost: 200
  grant: perk
  form: dragon_form

This syntax is valid Format 1 source and preserves these semantics:

  • kind: form is block-only and requires a package-local stable handle; it inherits the owning choice’s visible name, conventional description and visual content, and tags unless overridden
  • the initial amendment creates Jumper forms only; companion forms require a separate design rather than silently treating the companion as a form or routing the form’s perks into that companion’s profile
  • a form is a distinct record owner; a form-owned perk stores the target form’s stable runtime ID instead of an actor ID
  • form-owned perks appear only on the target form’s profile and form detail surfaces; they do not appear in the Jumper’s Inventory, Inventory Stats, or any companion profile
  • form: <handle> on a block-form perk grant resolves in the package-wide form-handle namespace; references may cross sections and files and may be forward references
  • form: <handle> directly on a choice targets that choice’s single grant: perk shorthand; it is invalid without exactly one shorthand perk grant, and choices with multiple or customized grants use block form to keep ownership unambiguous
  • the form reference is authored and fixed; it does not present a form selector to the user and does not permit runtime retargeting
  • a targeted perk depends on its referenced form grant being active; the application disables or rejects acquiring the perk without that form, and removing the form requires impact review for active dependent perk choices
  • renaming a form does not retarget or detach its perks because references use the authored form handle and persisted records use the form’s stable runtime ID
  • the purchasing actor pays the choice cost once under ordinary cost rules; assigning the perk to a form does not transfer the cost or resource balance to that form
  • rank and quantity metadata belong to each resulting form-owned perk record under the same explicit, separate semantics as actor-owned records
  • conditional text and placeholders initially evaluate against the purchasing Jumper’s current Jump choice/property context; exposing form-specific properties to expressions would be a separate amendment
  • the evaluator must reject or disable form grants and form-targeted perk grants while rendering a companion actor, rather than accidentally creating or modifying Jumper forms from companion purchases
  • the schema amendment must add positive and negative conformance fixtures for form identity, cross-section and forward references, block and shorthand ownership, absent or ambiguous shorthand grants, missing and duplicate handles, inactive dependencies, companion evaluation, removal, and historical projection

Companion-Owned Perks and Currency

Format 1 uses one companion: <handle> field to route grants to either a newly purchased companion or a group of runtime companions selected by an import. This is authored ownership, not a recipient picker shown to the user.

A purchased companion uses the companion grant handle. Scalar companion shorthand uses its owning choice handle:

choice
  handle: aster
  name: "Aster"
  grant: companion

  grant
    kind: resource
    resource: jump_points
    amount: 500
    companion: aster

  grant
    kind: perk
    name: "Boundary Instinct"
    companion: aster

An import declares its own target handle because the selected companions have runtime identities unknown to the author:

input
  handle: travelers
  selection: companions

  grant
    kind: companion-import
    handle: horizon_company

  grant
    kind: resource
    resource: jump_points
    amount: 500
    companion: horizon_company

  grant
    kind: perk
    name: "Company Pathfinder"
    companion: horizon_company

Ordinary perk shorthand can target the same handle without a block:

choice
  handle: field_training
  name: "Field Training"
  grant: perk
  companion: horizon_company
  • block-form companion and companion-import grants require unique package-wide handles; scalar grant: companion uses its owning choice handle
  • companion: <handle> is valid only on perk and resource grants; items, traits, properties, forms, and companion grants cannot target companions
  • a perk target may resolve to one purchased companion or every selected companion represented by an import handle
  • a positive targeted resource grant is what makes a purchased or imported companion participate in the current Jump and appear in Make choices as; a targeted perk alone only accrues to the companion profile
  • companions start with zero of the Jump’s resources and receive only explicit targeted currency plus ordinary resource grants from choices they subsequently make
  • resource and perk targets use the same package-wide companion namespace, may cross sections and files, and may be forward references
  • the choice-level companion shorthand target requires exactly one scalar perk grant; multiple or customized grants use block form
  • a grant cannot specify both form and companion; forms remain valid targets only for perks and cannot receive currency, items, or other grant kinds
  • companion-targeted grants evaluate from the Jumper’s active choice/input context and are not recursively applied while rendering a companion actor

Finalized Association Rules

  • choice.name is required; the earlier shorthand list that displayed it without a required marker does not make nameless choices valid.
  • Block-form visible grants support perk, item, companion, and trait. This makes the already-agreed partial inheritance and grant-specific tags expressible without introducing another declaration shape.
  • Conditional variants of singular fields belong to that field on the current owner. Because option is repeatable, an option when ... variant belongs to the immediately preceding base option at the same indentation. A new base option starts a new variant group. This preserves scalar options and avoids option blocks.
  • section owns text, images, choice sources, and handled associations to top-level choices. Interactive input blocks remain choice-owned because their values activate choice mechanics and grants.
  • Grant fields are kind-checked. Resource and property mechanics cannot accidentally accept visible-content fields, and companion imports remain valid only directly under a companion-selection input.
  • Every authored layout has exactly one handled container root. Grid requires columns from 1 through 12; typed leaves use their matching owner-local namespace; expand and compact direct choice placement remain section-layout-only.

Schema Change Policy

Secure .jmp transport

Package archives are untrusted. Import streams actual decompressed bytes and never trusts ZIP-declared sizes. It allows no more than 256 regular entries, a 100:1 per-entry and overall compression ratio, root .jdef files, and PNG/JPEG/GIF/WebP/AVIF files below assets/. Traversal, absolute and non-canonical names, normalized or case-folded collisions, links, devices, encryption, multi-disk or nested archives, corrupt headers, CRC or size disagreement, trailing polyglot data, unsupported files, signature/extension mismatch, and malformed images are blocking failures.

Images are decoded within bounded memory before their bytes are exposed. Width and height are each limited to 8192 pixels, each image to 24 megapixels, and the package to 64 megapixels. The staged package becomes visible only after archive, source, schema, semantic, reference, and asset validation all succeed.

Effective byte budgets default to 64 MiB compressed archive, 2 MiB per definition, 16 MiB per asset, and 96 MiB expanded. Validated Developer overrides can increase byte budgets only; path, ratio, signature, decoder, schema, and atomicity safeguards remain mandatory.

Corrections that only improve diagnostics, recovery, documentation, or editor assistance may retain format 1 when they do not change the valid source language. After the first release, any new declaration, field, scalar form, node kind, or contextual placement that changes validity requires an explicit schema revision and migration review. Before that release, the agreed identity amendment is incorporated directly. The initial fixtures deliberately cover a minimal informational Jump, a representative layout-and-choice package, a valid warning-bearing WIP case, and a duplicate-resource cost error; implementation expands this corpus whenever a parser or validator defect is found. Building exhaustive positive and negative fixtures for every declaration, node, diagnostic, and interaction is an implementation step after the design contract is complete; it does not remain an open language-design decision.
