Living preference registry

Settings design

The authoritative list of configurable application behavior, including defaults, allowed values, scope, persistence, and decision status.

Current state: appearance, accent color, motion, Editor save mode, Chain Tracker behavior, notification presentation, keybinding overrides, and the user tag profile are confirmed. Session logs are available as a Developer utility rather than persisted settings.

Purpose

This page prevents preferences from being invented ad hoc during feature implementation. A behavior belongs here only when users have a meaningful reason to choose between supported alternatives. Document semantics, package content, and author presentation choices belong in the Jump package or markup—not in application settings.

Settings Principles

  • Defaults should serve most users without requiring setup.
  • Settings solve genuine preference, accessibility, environment, or compatibility needs; they do not replace a clear product decision.
  • Application settings are user-local and must not alter the portability or meaning of a Jump package.
  • Each setting has a stable key, explicit default, bounded value type, scope, validation rule, and migration story.
  • Unsupported or invalid stored values fall back safely to the documented default and produce a recoverable diagnostic.
  • Security-sensitive values and filesystem permissions are not ordinary settings and must not be stored in this registry as plain preference data.

Presentation and Routing

Settings uses the agreed route-backed overlay. Opening it from Home or a workspace pushes /settings, preserves the prior route underneath as inert content, and restores that route on Close, Escape, or Back. Opening /settings directly renders the same content as a full page.

The initial surface includes persistent categories, global setting search, visible defaults, and a per-setting Reset action. The Settings frame keeps one compact, stable height across categories; each category and complex editor scrolls inside its own content region instead of resizing the dialog. Changes normally apply immediately; settings that cannot apply safely without restart must say so before the user changes them.

Settings Search

Search covers every category and matches visible labels, stable setting keys, descriptions, allowed values, and maintained aliases. Results identify their owning category. Selecting a result clears the query, opens that category, and focuses the setting. Clearing an unfinished search restores the category that was selected before searching.

Accent Color Safety

appearance.accentColor stores only a normalized six-digit sRGB hex value. The raw base color may be used for decorative swatches, but the application derives separate accessible tokens for text, focus indicators, borders, filled controls, and subtle surfaces in Light and Dark themes. Derived tokens must retain the selected hue as closely as possible while meeting the applicable contrast requirement. Raw setting text must never be interpolated directly into styles.

Notification Projection

Toast preferences control the user-facing projection of registered events described in Logging Design. Disabling a toast class does not suppress its session log entry, diagnostic, state transition, or undo record. Input-driven candidates are debounced for 500 ms and repeated matching events update one toast rather than creating a stream of duplicates.

Interactive Settings Surface

The category navigation, accent picker, search, notification preview, tag-profile editor, and Developer session-log viewer are interactive. Changing the accent updates this Settings preview while preserving the current gold as the Reset default. The Tags page uses the accepted editor from Tag System Design.

Tag Profile Scope and Transfer

  • The Tags page edits tags.profile; it does not add tag relationships or presentation fields to Jump markup.
  • Built-in categories are always present. Normalized strings found on accrued records are synchronized into the editor, and users may also enter strings manually.
  • Parents, reciprocal alias links, and badge overrides are user-local. Changing them affects search expansion and rendering without rewriting imported content.
  • The tag profile has dedicated versioned JSON import and export because it is intentionally shareable. Acquired records and Jump source are never included.
  • Per-tag Reset restores a built-in preset or returns a custom tag to parent-derived presentation, depending on the selected tag’s source.
  • Manual and imported profile-only tags may be deleted. Deletion automatically removes their alias links and reparents direct children; built-ins and tags sourced from accrued content remain protected.

Persistence and Migration

  • Settings persist independently from Jump packages and Chain records.
  • The persisted object carries a schema version and is migrated before use.
  • Missing keys receive current defaults; migrations do not rewrite unrelated preferences.
  • A Reset action restores one setting, one category, or the complete registry without deleting projects or chains.
  • General preference import/export remains deferred. The tag profile is the explicit exception and has its own versioned JSON transfer format.
  • Developer session logs and the debug-capture toggle never persist; every application launch starts with an empty log and debug capture disabled.

Setting Definition Template

New settings added to this document should record:

Key
Stable namespaced identifier.
Status
Candidate, agreed, deprecated, or removed.
Scope
Application, Editor, Chain Tracker, accessibility, or another explicit owner.
Type and values
Bounded value representation and validation rules.
Default
Behavior when the key is absent or invalid.
Application timing
Immediate, next workspace load, or restart required.
Persistence
Where it is stored and whether it may synchronize or export.
Rationale
The concrete user need that justifies configurability.
