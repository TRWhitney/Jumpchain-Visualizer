Simple metadata and user presentation draft

Tag system design

Free-text author metadata that makes accrued perks, items, companions, and other records searchable while supporting expressive, user-overridable badges.

Status: tag design settled. Jump authors supply only repeated string tags. The application supplies badge defaults and search normalization; optional relationships, presentation customization, static text effects, and bounded animation belong to the user and do not extend the Jump markup.

Goals

  • Authors apply useful string tags without declarations, handles, schemas, or a central vocabulary.
  • Tags inherited by granted perks, items, companions, traits, and properties become the main search vocabulary for a chain’s accrued content.
  • Parent/child relationships make broad category searches useful and keep category badge palettes visually coherent.
  • Tag categories support filtering and aggregate questions such as how many accrued perks are tagged “Magic.”
  • Built-in defaults make every tag readable; users control any custom badge presentation and motion.
  • Unsafe CSS, unreadable color combinations, flashing effects, and invalid user relationships are rejected or safely normalized.

Authoring Model

A tag in a Jump document is only a string. There are no tag declarations, tag handles, relationship blocks, or author styling fields.

choice
  handle: reality_warping
  name: "Reality Warping"
  tag: "Elemental Magic"
  tag: magic

  grant
    kind: perk
    tag: "Reality Alteration"
  • Bare and quoted values are both strings.
  • Quoting allows whitespace, punctuation, or text that could otherwise be read as structural syntax.
  • Source text remains in the imported package, but runtime identity and badge text use the application’s canonical tag form rather than cosmetic author spelling.
  • The tag field is repeatable; repeating one canonical tag identity on the same owner is an error.
  • Tags carry no behavior. They do not grant mechanics or imply affordability.

Normalization

  • Canonical identity applies Unicode compatibility normalization and Unicode case folding.
  • Every run of whitespace, underscores, and Unicode dash punctuation becomes one ASCII space; surrounding space is removed.
  • An empty canonical result is invalid. Matching canonical identities are the same tag across packages, and a duplicate on one owner is an error.
  • Badge text capitalizes the first letter of every canonical word except the lowercase particles a, an, and, as, at, but, by, for, from, in, nor, of, on, or, per, the, to, via, and vs. Particles remain lowercase even when first or last.
  • For example, lord_of_the-great_rings has canonical identity lord of the great rings and displays as Lord of the Great Rings.
  • Imported source spelling remains available in the package for diagnostics, but is not a separate identity or badge label.
  • User relationships and styles target canonical identities, not author-controlled spellings.

Taggable Content and Inheritance

The initial taggable semantic owners are:

  • choice
  • explicit grant blocks
  • future declarations that directly create trackable perks, items, companions, traits, properties, or resources

Text, image, layout, and theme declarations are not taggable. Sections remain untagged in v1 unless a concrete navigation need appears.

Common grants inherit the choice’s tags under the existing grant-inheritance rule. A block-form grant may add grant-specific tags so one choice can produce separately searchable records. Tags are strictly additive: grant tags never replace or remove inherited choice tags, and there is no tag-removal field.

Relationship Model

Relationships are user settings keyed by normalized tag strings. None of this data is authored in or written back to a Jump document.

Parent and child

A user-defined broader/narrower relationship between two strings. The draft allows one parent per string in v1, preventing cycles and keeping derived colors predictable.

Aliases

Separate strings that a user chooses to make search-equivalent, such as “Pyrokinesis” and “Fire Control.” Both source spellings remain intact.

These two relationships cover category hierarchy and equivalent wording without requiring Jump authors to coordinate a vocabulary. Hierarchy communicates category breadth only. Sharing a parent is not a separate relationship type.

Relationship Validation

  • A normalized string cannot parent or alias itself.
  • Parent cycles are errors.
  • A pair cannot simultaneously be aliases and have a parent/child relationship.
  • Aliases resolve symmetrically.
  • Removing or changing a relationship never rewrites source tag strings.

Built-in Top-Level Categories

The application provides twelve top-level category tags as a stable summary layer. They do not add declarations to Jump markup. Authors still write ordinary strings, while the user’s relationship settings determine which category contains each string.

Physical

Body, health, senses, forms, and bodily capability.

Mental

Memory, cognition, learning, emotion, and will.

Social

Communication, relationships, leadership, and reputation.

Magic

Spellcraft and explicitly magical systems or techniques.

Spiritual

Souls, spirits, faith, and spiritual practices.

Technology

Science, computing, engineering, and technological systems.

Crafting

Making, repairing, enchanting, cooking, and other creation skills.

Combat

Offense, weapons, tactics, and direct fighting capability.

Defense

Protection, resistance, recovery, and survival.

Stealth

Concealment, infiltration, disguise, and evasion.

Meta

Chain, Jump, perk, and other rules-facing effects.

Miscellaneous

The fallback for tags with no path to another top-level category.

  • The top-level names and their chart order are built in so profiles remain comparable and the radar does not change shape because categories were reordered. Clockwise from the top, the order is Social, Mental, Spiritual, Magic, Meta, Stealth, Physical, Combat, Defense, Crafting, Technology, and Miscellaneous. Meta and Miscellaneous separate the mental/spiritual and physical/material halves.
  • Users may override every category’s badge style and color.
  • A user may assign any ordinary tag to a category by giving it a parent whose chain reaches that category.
  • An ordinary tag with no path to one of the other eleven categories is treated as a child of Miscellaneous. This fallback is derived and does not write a parent into the Jump document.
  • An alias uses the category of the string it aliases. Conflicting category paths are rejected rather than guessed.

Category Counting

The radar represents inventory counts, not ratings. Each axis is the number of accrued records carrying that category tag or one of its descendants. Every axis label uses its category color and a legible display size; compact read-only radar projections increase the label size further to compensate for scaling.

  • A record counts at most once in a category, even when several of its tags resolve to that category.
  • A record may count in several categories when its tags resolve to different top-level categories.
  • Aliases do not add another count.
  • Inherited and grant-specific tags count in the same way as direct tags.
  • A tagged record counts once under Miscellaneous when at least one of its tags has no other category path. Untagged records are not silently categorized.
  • Every radar axis uses the same zero-based count scale. Exact values remain available beside the chart.

Radar and Breakdown Interaction

  • Clicking an axis, point, label, or sidebar category selects it, colors its header, and emphasizes the radial line. This changes inspection state only.
  • The sidebar can sort by occurrence count or tag name. Sorting changes only the list order; radar axes, pie slices, colors, and chart geometry remain fixed.
  • Double-clicking the already selected category opens its pie breakdown. The visible Open breakdown button provides the same action without requiring a double-click.
  • Every breakdown includes records tagged directly with the current category as well as its child tags.
  • A pie shows at most nine named slices plus one ellipsis slice. The ellipsis represents the combined remainder; opening it shows the next largest hidden elements without losing their total.
  • Hovering a slice highlights its sidebar row and exposes its name, count, and compact alias summary. Hovering a row provides the same correlation.
  • Clicking a slice or sidebar row pulls that slice outward. Double-clicking a slice with children opens its child breakdown.
  • A visible Back button unwinds one level at a time, including an ellipsis remainder, until it returns to the radar. Breadcrumbs can jump directly to an earlier level.
  • Aliases never become separate slices or add counts. The sidebar shows the first alias followed by +N; the complete alias list remains available as hover/focus text.
  • The live Settings preview is the canonical tag-badge renderer used by Inventory, record details, Forms, Companions, and every other application projection. Rainbow uses a fixed high-chroma color cycle so it remains perceptible even when the configured starting text color is white; Reduced Motion still renders the unanimated configured text color.
  • For keyboard use, Enter selects a radar category and Enter again opens it. In pie mode, Enter pulls out a row and Enter again drills into it when children exist.

Tag Profile Editor Mock

The profile editor is independent from the radar and edits the user’s reusable tag list. It always includes the twelve Primary Tags and the application’s larger Built-In Tags catalog. The left pane presents Primary Tags, Built-In Tags, and Acquired Tags as independently collapsible sections; an active search temporarily reveals matching entries even when their section is collapsed. Refresh acquired tags explicitly scans tag strings declared by every installed Jump package, compares normalized strings against both canonical names and aliases, and adds only missing strings under Miscellaneous. It does not run automatically or alter installed Jump documents. Manually entered strings appear in Acquired Tags with the source label Custom, while detected strings use Installed jump.

JSON Transfer Format

Users can export their complete tag profile as versioned JSON and import a shared profile by file or pasted text. The mock uses pasted text so the data is visible during design.

{
  "schemaVersion": 1,
  "tags": [
    {
      "name": "Pyrokinesis",
      "source": "acquired",
      "parent": "Magic",
      "appearanceSource": "custom",
      "presentation": {
        "background": "gradient",
        "colors": ["#d9480f", "#9b330b", "#df753f"],
        "positions": [0, 42, 100],
        "angle": 120,
        "borderColor": "#d9480f",
        "borderWidth": "thin",
        "corners": "pill",
        "padding": "compact",
        "textMode": "auto",
        "textColor": "#ffffff",
        "weight": "bold",
        "fontStyle": "normal",
        "decoration": "none",
        "textEffect": "none",
        "animation": "none"
      }
    },
    {
      "name": "Fire Control",
      "source": "acquired",
      "parent": "Magic",
      "appearanceSource": "derived"
    }
  ],
  "aliasLinks": [
    { "tags": ["Fire Control", "Pyrokinesis"] }
  ]
}
  • Export contains built-in overrides, custom tags, parents, aliases, and bounded presentation values. It never contains acquired records or Jump source.
  • Import validates the schema and shows conflicts before applying changes. Merge is the default; replacing manual/imported tags and current overrides requires an explicit choice. Built-ins and strings still present on acquired records cannot be removed by import.
  • Built-ins match by their stable built-in name. Imported custom tags match by normalized string.
  • source records export provenance only. A newly shared tag is labeled Imported; a matching local tag retains its existing provenance.
  • Literal search aliases such as Vehicle/Vehicles serialize with their canonical tag. Each reciprocal relationship between two canonical tags is serialized once in aliasLinks; direction and duplicated declarations are not part of that relationship model.
  • Unknown fields do not execute or become CSS. Invalid colors, relationship cycles, duplicate normalized strings, and unsupported values are rejected with diagnostics.
  • Text effects serialize as none, outline, shadow, or glow. Animation serializes as none, rainbow, marquee, ghost, or bounce.

Search and Filtering

The Chain Tracker search index for every accrued record contains:

  • the record name and descriptive text
  • direct canonical tag identities and their generated badge labels
  • aliases from user relationship settings
  • ancestor strings from user relationship settings
  • the originating Jump and grant kind

With the example user relationships configured, typing “fire control” finds a Pyrokinesis-tagged perk, while typing “magic” finds direct Magic records and descendants such as Pyrokinesis. Without those relationships, search matches only the normalized strings actually present in the imported content. A selected parent filter includes descendants by default and offers an Exact option.

Search is case-insensitive and tolerant of spacing, but not fuzzy enough to merge semantically unrelated tags. Misspellings may be suggested separately without changing stored identity.

Badge Presentation Model

A badge presentation may define bounded values in these groups:

Text

Foreground color or automatic contrast; normal, medium, or bold weight; normal or italic style; optional underline or strike only where it does not imply interaction.

Text effects

None, Outline, Drop shadow, or Glow. These are bounded static presets rather than arbitrary effect parameters, and the renderer may suppress an effect when necessary to preserve legibility.

Background

Transparent, solid color, or a two-to-six-stop linear gradient with a bounded angle and positioned stops. Every point behind text must remain readable.

Motion effects

None, Rainbow, Marquee, Ghost, or Bounce. Rainbow cycles text hue from the configured foreground; Marquee turns one letter gold at a time; Ghost fades the text between full and low opacity; Bounce lifts letters in sequence to form a wave.

Border and shape

Border color and width, compact-to-roomy padding, and bounded corner styles. Shape may reinforce category relationships but cannot obscure the label.

Fallback

A static, solid, high-contrast badge is always available when a requested effect cannot render safely.

Badge List Rendering

When a record has several tags, their badges render as one horizontal list beside one another with a small consistent gap. The list wraps onto another horizontal row only when the available width is exhausted; tags are not presented as a vertical field-per-line list.

Canonical rendering invariant: every application consumer, including rendered Jumps, Inventory, record details, Forms, Companions, and Settings previews, renders the same canonical badge component and its complete computed presentation. Consumer CSS may lay out direct badge elements but must not recolor, pad, border, round, animate, or otherwise style a badge or any descendant inside it.

Known integration failure to prevent: a broad consumer selector such as .choice-tags span also matches the canonical badge's internal animated-text span. That produces a false inner capsule even though the canonical component is present. Select only direct non-canonical fallback children, and visually compare each new consumer with an existing Inventory or Tag Manager badge. DOM names and component usage alone are not sufficient verification.

Presentation Precedence

  1. Accessibility enforcement and platform capability constraints.
  2. User override for one normalized tag string.
  3. Appearance derived from that tag’s configured parent.
  4. The built-in category preset or deterministic application fallback.

Jump authors have no presentation layer for tags. Built-in defaults ensure every string has a badge, while the Tags page in Settings provides user customization.

User Override Storage

User relationship and presentation rules live in the tag profile in application settings, never inside an imported Jump or Chain record. Presentation is stored for an exact canonical tag identity; descendants without their own override derive appearance from their configured parent.

Overrides change search expansion or rendering only. They never rewrite imported content. A rule that no longer matches any accrued content becomes orphaned and can be reassigned or deleted.

Relationship-Derived Colors

Automatic color shifting keeps descendants inside a bounded family derived from their parent:

  1. A user-selected color is an anchor. Without one, a stable hash of the normalized string produces a deterministic built-in hue.
  2. A string with a configured parent inherits that parent’s color family, then its badge background, gradient stops, and border receive a bounded hue, saturation, and lightness shift. This applies to shipped built-in children, refreshed acquired tags, and manually entered tags using derived appearance.
  3. The normalized child tag name is only the stable seed for that color shift; it does not change the tag’s label, text, structure, or other presentation. Adding or reordering siblings does not recolor existing tags.
  4. User-configured aliases share a badge style unless one string has a more specific user override.
  5. A user color override on a child starts a new anchored sub-family for its descendants.
  6. Gradient stops shift together in the same perceptual space.
  7. Final foreground, background, border, and focus colors are adjusted for the active Light or Dark theme and required contrast.

Color is never the only indication of hierarchy or aliasing. Labels, relationship text, grouping, and optional non-color badge cues remain available.

Editor Authoring Impact

  • Structured choice and grant editors use a free-entry string control with removable chips and normalized duplicate prevention.
  • Completion may suggest strings already used in the current package or workspace, but it always accepts a new string.
  • Source completion suggests existing strings while accepting ordinary bare or quoted values.
  • There is no Tags declaration group, relationship editor, or badge-style editor in the Jump Editor.
  • User relationship and presentation management belongs to the separate tag-profile editor, not Jump authoring.
  • Settings exposes this editor as its own Tags category; the standalone mock remains the detailed design reference.
  • Diagnostics may flag normalized duplicates and offer non-destructive warnings for likely spelling variants.

Tag Profile Reset and Dependency Rules

  • The twelve Primary Tags are fixed top-level radar axes. The expanded Built-In Tags catalog supplies more than 150 reusable descendants with stable IDs, meaningful parents, preset presentation, and search aliases such as Vehicle/Vehicles. Non-primary built-ins may be reparented and otherwise customized without changing their protected built-in identity.
  • For a built-in tag, Reset discards its user presentation override and restores its application preset. It does not remove aliases or the selected parent.
  • For an acquired, manual, or imported tag, Reset discards its presentation override and derives its colors and other appearance fields directly from its current parent. Newly refreshed and manually entered tags begin under Miscellaneous. Later parent appearance changes continue to flow into them until the user edits a presentation field again.
  • Editing any presentation control changes the selected tag’s appearance source to Custom override. Relationship and alias edits do not.
  • Controls unavailable because of another value show a lock treatment and the value that must change: gradient controls require Gradient, solid color requires Solid, and custom text color requires Custom text color mode.
  • Gradient endpoints remain at 0% and 100%. Users can add, select, recolor, drag, reposition, or remove interior stops; a gradient contains two to six stops.
  • Aliases are reciprocal links between two tags already in the profile. Adding or removing the link from either tag updates both views.
  • Delete is available only for manual or imported profile-only tags. Deleting one automatically unlinks its aliases and reparents its direct children to its former parent. Built-ins and tags discovered from installed Jumps cannot be deleted.
  • The animation control uses a select-style listbox because native option elements cannot reliably animate. Rainbow, Marquee, Ghost, and Bounce preview directly on their own option labels and on the selected-value label.

Chain Tracker Impact

  • Accrued-content search indexes inherited and grant-specific tags at import time and updates the index through package migration.
  • Result cards display a bounded number of badges and expose the remaining tags without forcing every badge into the primary layout.
  • Selecting a badge creates a filter; parent filters include descendants and can switch to Exact.
  • User-configured aliases expand filters and saved queries without replacing the source strings.
  • The Tracker never infers mechanical rules, affordability, or outcomes from badge color or animation.

Accessibility and Safety

Tag-profile entries use the shared application context menu for Edit, Reset appearance, and conditional Delete. Only manual and imported tags expose Delete; built-in and acquired catalogue entries retain their established ownership rules. Actions target the clicked entry and reuse the visible editor commands.

  • Badge text meets 4.5:1 contrast against the least-contrasting point of its background or receives an opaque text backplate/outline that does.
  • Meaningful badge boundaries and interactive states meet 3:1 non-text contrast.
  • Color, gradient intensity, text effects, and animation never serve as the only indication of a category relationship.
  • Reduced Motion disables badge and relationship-transition animations. Rainbow returns to the original text color, Marquee removes its gold sequence, Ghost remains fully opaque, and Bounce remains on the baseline.
  • Automatically running animation can be disabled globally and never flashes at unsafe frequencies.
  • Tag labels remain real text, resize and reflow, and expose any active user relationships to assistive technology.
  • Markup contains strings only. CSS declarations, URLs, scripts, custom fonts, and arbitrary animation definitions are not tag fields.

Validation and Diagnostics

Error

Empty or invalid source string, normalized duplicate on one owner, user relationship cycle or conflict, invalid user color, unsupported effect, or unsafe animation.

Warning

Likely spelling variant, unreadable user palette that requires adjustment, excessive user hierarchy depth, or a user rule with no matching accrued content.

Information

A built-in badge default is active, a user relationship expanded search, or a static reduced-motion fallback replaced animation.

Research Basis

  • Existing Jumpchain organization practices commonly use broad categories including Physical, Mental, Social, Magical, Stealth, Crafting, Spiritual, Meta, Technological, and Other; the working set extends that base with Combat and Defense. JumpChain community organization discussion
  • Charts should remain visual enhancements with exact data available as a text description or semantic table, which is why the radar is paired with visible counts. Government Analysis Function accessible chart checklist
  • SKOS distinguishes alternate labels from broader and narrower concept links, supporting separate alias and parent/child behavior. W3C SKOS Reference
  • Perceptually uniform Oklab/OkLCh spaces are designed for evenly spaced color interpolation and hue-preserving mixes. CSS Color Module Level 4
  • Small text requires 4.5:1 contrast, while meaningful component boundaries and states require 3:1. WCAG 2.2
  • Color cannot be the only visual means of conveying meaning. W3C Use of Color guidance
  • Nonessential motion should honor user preferences and be disableable. W3C Animation from Interactions guidance

Settled Boundary

  • Authors provide repeated strings only. Tags have no declarations, handles, relationships, or presentation fields in markup.
  • The application provides built-in badge defaults.
  • Users own any relationship graph and presentation customization, stored outside imported Jump documents.
  • The radar and drilldown are non-editing count representations and remain independent from tag customization.
  • The user tag-profile editor covers built-ins, tags discovered on acquired records, and manually entered strings.
  • Tag profiles are portable as versioned JSON. Static text effects and animations both use bounded application-defined presets.
  • In Light mode, profile Import, Export, and Reset actions use neutral light controls, and tag-list or animation-option interaction states stay on light secondary surfaces. Dark mode retains its established controls and interaction palette.

Settled User-Layer Decisions

  1. The twelve-category working set is Physical, Mental, Social, Magic, Spiritual, Technology, Crafting, Combat, Defense, Stealth, Meta, and Miscellaneous.
  2. Miscellaneous is a derived fallback for otherwise uncategorized tags; untagged records remain outside the category chart.
  3. The radar uses raw accrued-record counts, counts a record once per category, and always exposes the exact values in a table.
  4. Aliases are separate strings made search-equivalent by user settings.
  5. Each normalized string has at most one user-configured parent in v1.
  6. Parent searches include descendants by default, with an Exact option.
  7. JSON import defaults to merging by normalized string, while replacement remains an explicit alternative.
  8. Alias relationships are undirected links stored once; the editor reflects the link from both tags rather than accepting duplicated free-text lists.
  9. Custom tags default to parent-derived appearance. Editing a presentation field creates an override; Reset removes it and returns to the parent-derived appearance.
  10. Gradients use two fixed endpoint stops and up to four removable, positionable interior stops.
  11. Choice tags are inherited by their grants, while block-form grants may add their own tags for separately searchable outputs. Tag composition is additive only.
  12. Manual and imported profile-only tags may be deleted; deletion automatically unlinks aliases and reparents direct children.
  13. The animation vocabulary is None, Rainbow, Marquee, Ghost, and Bounce, with static Reduced Motion equivalents.

Tag Design Status

No tag-system design decisions are currently open. Implementation may expose practical issues that require revisiting these decisions, but animation, relationships, inheritance, search behavior, presentation, profile lifecycle, and transfer are all specified for the current version.
